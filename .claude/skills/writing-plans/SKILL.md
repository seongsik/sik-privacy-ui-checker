# Writing Plans (경량 계획서)

설계서가 설계를, 구현이 코드를 담는다. 계획서는 **무엇을 어떤 순서로 하고 언제 끝난 것으로 보는지**만 담는다. PM이 개요 절만 읽어도 범위·순서·완료 기준을 알 수 있어야 하고, 에이전트는 태스크 절만 읽어도 작업을 시작할 수 있어야 한다.

**Announce at start:** "writing-plans 스킬로 계획서를 작성합니다."

**저장 위치:** `docs/plans/YYYY-MM-DD-<feature>.md` (템플릿 `templates/plan.md`). 설계서는 `**Spec:**`에 경로로 연결한다.

## 형식

템플릿을 그대로 따른다. 구성:

1. **헤더** — Goal 한 문장, `**요구사항:**`(REQ ID 명시적 목록), `**Spec:**`, `**승인:** (미승인)`.
2. **개요** — 배경과 목표(2~3문장), 범위(포함/제외), 검수 조건(관찰 가능한 조건 2~4개), 위험(1~3개와 대응), 실행 방식, 그리고 표 `| 태스크 | 요구사항 | 가중치 | 의존 | 완료 기준 |`.
3. **Global Constraints** — 설계서의 프로젝트 전역 제약을 한 줄씩 그대로 옮긴다.
4. **Review Focus** — 테스트가 직접 다루지 않지만 사용자가 겪을 입력·조건 3~5줄. 각 줄에 어느 태스크의 검증이 다루는지, 또는 다루는 태스크가 없음을 적는다.
5. **태스크** — `### Task N: 제목 [REQ-001, REQ-002] [w=2]` 아래에 **목표**(한 문장), **대상**(생성·수정·삭제 파일), **의존**(없음 또는 Task N), **인터페이스**(선택: 선행에서 받는 이름, 후행에 주는 이름), **완료 기준**(관찰 가능한 결과 1~3개), **검증**(명령 한 줄과 `Expected:` 한 줄), 체크박스 4개(테스트 작성·실패 확인 / 구현 / 검증 명령 통과 / Commit `Refs:`).

## 규칙

- **코드 금지.** 구현 코드, 테스트 코드 본문, 2~5분 단위 Step 분해를 쓰지 않는다. 코드가 필요한 설계 결정은 설계서에 둔다. 허용되는 코드는 검증 명령 한 줄뿐이다.
- **태스크당 15줄 안팎.** 넘으면 태스크를 나눈다.
- **검증은 하나.** 태스크 전체를 판정하는 명령 하나와 기대 결과 한 줄. `executing-plans`가 이 `Expected:`를 실제 출력과 대조하고, `task-done`에 같은 명령을 넘긴다.
- **검증 명령이 곧 그 태스크의 RED 테스트다.** 실행자는 구현 전에 이 명령을 실행해 실패를 확인하고, 세부 단위 테스트는 BASELINE 4번과 `test-driven-development`에 따라 스스로 설계한다(계획서에는 테스트 케이스가 없다). 문서·설정만 바꾸는 태스크에서는 첫 체크박스 "테스트 작성, 실패 확인"을 "검증 명령 실패 확인"으로 읽는다. 검증 명령은 저장소 안에서 자족적이어야 하며 임시 디렉터리의 스크립트에 의존하지 않는다.
- **모든 태스크에 요구사항 태그.** 가중치 `[w=N]`은 PM과 합의한 상대 크기(생략 시 1).
- **의존은 정직하게.** 선행 태스크의 산출(파일, 함수 이름, 문구)을 쓰면 의존과 인터페이스에 적는다. 병렬 조건 판정에 쓰인다.
- **설계서 문구 참조.** 경고 메시지, 열 이름, 필드명처럼 정확해야 하는 값은 계획서에 다시 쓰지 않고 설계서의 절 번호를 가리킨다.

## 자가 검토 (작성 직후, 스스로)

1. 설계서의 요구사항·절마다 담당 태스크가 있는가. 없으면 태스크를 추가한다.
2. 후행 태스크가 쓰는 이름이 선행 태스크의 인터페이스에 있는가.
3. 완료 기준이 모두 관찰 가능한가("잘 동작" 같은 표현 금지).
4. 태그 없는 태스크, 15줄을 크게 넘는 태스크, 코드 블록이 없는가.
5. Review Focus 각 줄이 태스크의 검증과 연결되는가.

## 실행 인계

계획서를 저장하고 자가 검토한 뒤 사용자에게 알린다.

> "계획서를 `docs/plans/<파일>.md`에 저장했습니다. 검토 부탁드립니다. 승인되면 executing-plans로 바로 시작합니다."

**기본은 Native(`executing-plans`)다. 실행 방식을 매번 묻지 않는다.**

**병렬 조건** (세 가지 모두 충족할 때만): 태스크 4개 이상, `**의존:** 없음`인 태스크가 절반 이상, 태스크 간 **대상** 파일 겹침 없음. 충족하면 개요의 "실행 방식"에 그 사실을 적고, 승인 요청에 한 문장을 덧붙인다.

> "병렬 실행 조건을 충족하므로 subagent-driven-development를 제안합니다. 비용은 태스크마다 구현·리뷰 컨텍스트 하나씩입니다. Native로 할까요, 병렬로 할까요?"

사용자가 "병렬로"라고 말하면 조건과 무관하게 `subagent-driven-development`를 쓴다.

**승인 후:** `**승인:**`을 `<git config user.name> YYYY-MM-DD`로 채워 commit하고(sdd-deliverables 규칙), 선택된 실행 스킬을 시작한다.
