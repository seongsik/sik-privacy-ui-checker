## 1. 목적과 범위

개발자와 개인정보 점검 담당자가 **운영 중인 웹서비스**의 개인정보보호 기준 준수 여부를 점검하는 Claude Code 스킬이다.
URL을 받으면 격리 브라우저로 확인된 메뉴를 모두 탐색해 증적을 수집하고, 법령·고시·지침 기준으로 판정해,
취약점마다 조치방안을 담은 HTML 보안성 검토 리포트를 만든다.

### 1-1. 합의된 결정

| 주제 | 결정 |
|---|---|
| 운영 원칙 | 운영 환경이다. 데이터를 절대 수정하지 않는다. |
| 브라우저 | Playwright 격리 브라우저(화면 표시, write_guard ON). 처음엔 Claude in Chrome을 기본으로 정했으나, 쓰기 요청을 네트워크 단계에서 막을 수 있는 쪽으로 바꿨다. |
| 로그인 | 사용자가 격리 브라우저 창에서 직접 한다. Claude는 비밀번호 칸에 입력하지 않는다. |
| 능동 시험 | 테스트 계정으로, 항목마다 사용자 승인 후. 입력은 사용자가 하고 스킬은 안내·관찰·기록·판정한다. |
| 점검 기준 | 안전성 확보조치 기준과 안내서, 개인정보 보호법·시행령, 정보통신망법·시행령, 표준 개인정보 보호지침 전부. |
| 탐색 | 메뉴맵을 자동 수집하고 사용자가 확인한 목록만 방문한다. 반복 화면은 대표 화면만. |
| 판정 | 취약·권고·양호·점검불가·해당없음. 취약·권고에만 위험도 상·중·하. 상세 페이지는 취약·권고만. |
| 구조 | A안: 일괄 수집 후 판정. 수집물이 곧 증적이다. |
| 리포트 | 단일 HTML. 리포트 개요 + 취약점 하나당 한 페이지. 좌측 목차는 사이트 메뉴 하위 위험도 내림차순. |
| 캡처 | 개인정보는 픽셀화(블러는 복원 위험이 있어 쓰지 않음), 문제 영역에 번호 박스. |

### 1-2. 범위 밖

- 다른 정보주체의 개인정보를 실제로 조회하게 되는 시험(IDOR 파라미터 변조 등). 그 자체가 위반이 될 수 있다.
- SQL 인젝션·XSS 같은 공격형 취약점 진단. 이 스킬은 개인정보보호 기준 점검이다.
- CAPTCHA 풀기, 봇 차단 우회.
- TLS 버전·암호군 판정의 자동화. 브라우저로 볼 수 없으므로, 사용자가 직접 실행한 openssl 결과를 받으면 반영하고 없으면 점검불가로 둔다.
- 무차별 자동 순회(링크를 따라 전 사이트를 도는 것).

## 2. 전체 흐름

| 단계 | 하는 일 | 사용자 개입 | 사이트 접속 |
|---|---|---|---|
| 0. 착수 | URL, 승인 정보(승인자·범위·기간), 적용조건 질문지를 `intake.json`에 기록 | 승인 정보·질문지 답변 | 없음 |
| 1. 로그인 | 격리 브라우저를 띄우고 로그인 화면에서 대기, 로그인 뒤 세션을 작업 폴더 밖에 저장 | 직접 로그인 | 있음 |
| 2. 메뉴맵 | GNB·LNB·사이트맵·푸터를 읽어 메뉴 트리 생성, 표본 묶기, 금지 후보 표시 | 목록 확인·수정 | 있음(읽기만) |
| 3. 수집 | 공개 화면(메인·로그인·회원가입·비밀번호 찾기·처리방침)과 확정 메뉴를 write_guard 아래 수집 | 없음 | 있음 |
| 4. 판정 | `auto_checks.py` 1차 후보 + Claude 검토로 관찰 항목 판정. 의심 화면은 그 화면만 재수집 | 없음 | 재수집 때만 |
| 5. 능동 시험 | 항목별 승인 → 해당 요청만 잠시 허용 → 사용자 입력 → 기록 → 원복 | 승인·직접 입력 | 있음 |
| 6. 나머지 판정 | 서면 항목은 점검불가(요청 자료), 적용조건 밖은 해당없음 | 없음 | 없음 |
| 7. 증적 처리 | 개인정보 가림, 번호 박스, 미리보기 육안 확인 | 원하면 함께 확인 | 없음 |
| 8. 리포트 | 단일 HTML 빌드, 기계 검증, 육안 검수 | 결과 검토 | 없음 |
| 9. 정리 | 원본·세션 파일 삭제 안내 | 삭제 실행 | 없음 |

단계마다 산출물을 파일로 남겨, 끊긴 단계부터 다시 시작하고 판정만 다시 돌릴 수 있다. 사이트에 접속하는 단계는 1·2·3·5(와 4의 재수집)뿐이다.

## 4. 데이터 형식

### 4-1. 점검 기준 `references/criteria/*.yaml`

초안 Markdown의 11개 필드에 `category`, `strength`, `default_risk`를 더한다.

```yaml
- id: SAFE-05-06-01
  title: 인증 실패 시 접근 제한
  category: 인증·접근통제
  basis: [{law: 안전성 확보조치 기준, article: 제5조제6항}, {guide: 안내서, page: 61}]
  strength: 의무            # 의무 | 권고 | 외부참고
  default_risk: 상
  applies_when: 모든 개인정보처리자
  type: 능동                # 관찰 | 능동 | 서면
  location: [로그인 화면, 관리자 로그인]
  method: …
  pass: …
  fail: …
  remediation: …
  evidence: …
  notes: …
```

- ID 규칙: 접두어(SAFE·PIPA·NET·STD)-조-항-일련번호. 조의2는 B(조의3은 C …), 항이 없는 조는 `00`.
- 취약점 유형(`category`) 7종: 인증·접근통제, 암호화·전송, 노출·출력, 동의·고지, 처리방침·권리보장, 광고성 정보, 관리체계(서면).
- 변환: 스크립트로 초안을 YAML로 바꾸고 사람이 확인한다. `strength`·`default_risk`는 Claude가 1차로 채운 뒤 사용자 확인을 받는다.

### 4-2. 메뉴맵 `menu_map.json`

```json
{"menus": [
  {"id": "M03-02", "path": ["마이페이지", "회원정보 수정"], "url": "/my/profile",
   "status": "visit", "sample_of": null, "reason": null, "auth": "user"}
 ],
 "deny_patterns": ["/logout", "action=delete"]}
```

`status`: visit | sample | exclude | blocked. `path`는 리포트 좌측 목차의 뼈대다.

### 4-3. 판정 결과 `findings.json`

```json
{"findings": [
  {"no": "V-003", "item_ids": ["SAFE-07-01-02"], "verdict": "취약", "risk": "상",
   "category": "암호화·전송", "title": "비밀번호가 URL 파라미터로 전송됨",
   "menu": "M01-01", "url": "https://…/login", "params": ["pw"],
   "inputs": "테스트 계정 로그인(비밀번호 값은 기록하지 않음)",
   "shots": [{"file": "img/V-003_1.png",
              "boxes": [{"n": 1, "left": 31.2, "top": 22.0, "width": 18.4, "height": 4.1}]}],
   "problems": [{"n": 1, "text": "로그인 요청 URL에 비밀번호가 평문으로 포함됨"}],
   "remediation": "…", "basis": "…(의무)", "evidence_refs": ["har:entry-42"],
   "active_test": null}
 ],
 "others": [{"item_id": "SAFE-04-01-01", "verdict": "점검불가", "reason": "서면 항목", "request": "내부 관리계획 최신본"}]}
```

- 캡처의 박스 `n`과 `problems`의 `n`은 1:1. 빌드 시 불일치는 경고.
- 번호(`no`)는 메뉴 순서 → 위험도 내림차순 → 취약·권고 순으로 정렬한 뒤 V-001부터 매긴다. 재판정하면 다시 매긴다.
- `inputs`에는 비밀번호·실제 개인정보 값을 적지 않고, 무엇을 입력했는지만 적는다.
- 능동 시험 항목의 `active_test`에는 승인 문구, 승인 시각, 허용한 요청(메서드·URL), 시도 횟수를 기록한다.
- 특정 메뉴에 속하지 않는 항목(보안 헤더, 처리방침 링크 등)은 `menu: "COMMON"`으로 두고 목차의 "공통(전 화면)" 아래에 둔다.

## 5. 리포트

CSS·JS·이미지를 내장한 단일 HTML. 좌측 목차 + 우측 본문, 본문은 한 번에 한 페이지. 주소 해시(`#overview`, `#V-003`)로 페이지를 바꾼다.

### 5-1. 좌측 목차

```
리포트 개요
검토결과 상세
 ├ 로그인
 │  ├ [상] V-001 …
 │  └ [중] V-002 …
 ├ 마이페이지 › 회원정보 수정
 │  └ [상] V-003 …
 └ 공통(전 화면)
```

- 메뉴 아래는 위험도 내림차순, 같은 위험도에서는 취약 → 권고.
- 취약점이 없는 메뉴는 목차에 넣지 않는다(개요 커버리지에는 남는다).
- 위험도 배지: 상 빨강, 중 주황, 하 회색.

### 5-2. 리포트 개요

1. 대상 사이트 정보: URL, 점검 기간, 점검자, 승인자, 범위, 점검 계정 역할, 점검 방식.
2. 적용 법령·가이드: 원문명, 판(고시 번호), 시행일. 시행일 확인이 필요한 조항은 각주.
3. 결과 요약: 판정별·위험도별 건수.
4. 취약점 목록: 좌측 목차와 같은 순서의 표(번호, 위험도, 유형, 취약점명, 화면 메뉴명). 행을 누르면 상세로 이동.
5. 점검 커버리지: 방문, 표본, 제외(사유), 접근 불가 메뉴.
6. 점검불가·해당없음 목록. 서면 항목은 요청 자료를 함께 적는다.

### 5-3. 검토결과 상세(취약점 하나당 한 페이지)

| 위치 | 내용 |
|---|---|
| 머리 | 취약점 번호, 위험도 배지, 판정, 취약점 유형, 취약점명 |
| 정보 표 | 화면 메뉴명, URL, 파라미터, 입력사항 |
| 캡처 | 가린 이미지(번호 박스 포함), 누르면 확대, 여러 장이면 차례로 |
| 문제점 | 박스 번호와 1:1인 번호 목록 |
| 조치방안 | 구체 조치(설정·코드 예시)와 관리적 조치 |
| 근거 | 조문, 근거 강도(의무·권고·외부참고), 안내서 쪽수 |
| 아래 | 이전·다음 버튼, 키보드 ←·→ |

### 5-4. 캡처 처리

- 번호 박스는 이미지에 직접 그린다(킷은 HTML 위에 얹는다). 캡처 이미지가 증적으로 따로 쓰일 때도 박스가 남아야 한다.
- 가림 기본은 9px 픽셀화 + 가장자리 3px 여유. 주민등록번호·카드번호·계좌번호 등은 불투명 박스.
- 가림 대상 측정은 킷 방식(정규식 패턴, 표 열, 입력칸 이름, 셀렉터, 모달 exclude)을 따른다. 이미지·캔버스 속 글자는 좌표를 손으로 지정한다.
- 완료 판정은 사람 눈: 배포 이미지 전부를 원본 크기로 열어 본다.

### 5-5. 인쇄

A4 인쇄 CSS. 개요가 앞에, 이후 취약점 하나가 한 쪽에서 시작한다.

## 6. 판정과 위험도

### 6-1. 판정

| 판정 | 뜻 | 상세 페이지 |
|---|---|---|
| 취약 | 법령·고시 의무 위반이 화면에서 확인됨 | 생성 |
| 권고 | 의무 위반은 아니나 안내서 예시·외부 기준에 못 미침, 또는 해석에 따른 판정 | 생성 |
| 양호 | 기준 충족 | 개요 집계만 |
| 점검불가 | 서면 항목, 승인하지 않은 능동 시험, 접근 불가 화면 | 개요 목록 |
| 해당없음 | 적용조건 밖 | 개요 목록 |

### 6-2. 위험도

| 위험도 | 기준 | 예 |
|---|---|---|
| 상 | 개인정보·인증정보가 권한 없는 자에게 바로 노출·탈취될 수 있음 | 평문 HTTP 로그인, 응답 속 주민번호 전체, 관리자 페이지 외부 노출, 인증 실패 제한 없음 |
| 중 | 다른 조건이 겹쳐야 노출되거나 정보주체 권리를 침해 | 세션 차단 없음, 마스킹 불일치, 동의 필수·선택 미구분, 처리방침 기재 누락 |
| 하 | 노출 가능성이 낮거나 형식 요건 미흡 | 처리방침 명칭·강조 표시, 권고 수준 항목 |

항목의 `default_risk`에서 시작해, 실제 노출 범위를 보고 Claude가 조정하고 사유를 남긴다.

### 6-3. 권고 기준값(법정 수치가 없는 항목)

고시·안내서가 수치를 정하지 않는 항목은 아래 외부 참고값에 못 미치면 **권고**로 판정하고, 근거에 "외부 참고"라고 적는다. 처리자가 자체 기준을 서면으로 제시하면 그 기준과 실제 동작의 일치 여부를 본다.

| 항목 | 외부 참고값 |
|---|---|
| 비밀번호 작성 규칙 | 2종 조합 10자 이상 또는 3종 조합 8자 이상(구 해설서 관행), 추측 쉬운·유출 비밀번호 거부(NIST SP 800-63B) |
| 인증 실패 제한 | 5회 이내 잠금 또는 지연 |
| 세션 자동 차단 | 30분 이내 |
| TLS | TLS 1.2 이상 |
| 마스킹 | 같은 항목은 화면 간 같은 규칙(안내서 FAQ) |

## 7. 안전장치

### 7-1. 데이터 수정 금지

| # | 장치 | 막는 것 |
|---|---|---|
| 1 | write_guard: GET·HEAD·OPTIONS 외 요청 차단, WebSocket 송신·`sendBeacon` 포함 | form 제출, 저장 API, 로그 전송 |
| 2 | 조회성 POST 허용 목록: 막힌 요청 중 조회용 경로는 사용자 확인 후에만 허용 | 무분별한 허용 |
| 3 | GET 금지 목록: 메뉴맵 금지 링크 + 기본 패턴(logout, delete, remove, withdraw, unsubscribe, approve, send 등) | 열기만 해도 상태가 바뀌는 링크 |
| 4 | 동작 제한: 탭 전환·모달 열기·펼치기·스크롤만. 위험 문구 요소 클릭 금지. alert·confirm 자동 취소 | 우발적 클릭 |
| 5 | 범위 제한: intake의 대상 도메인 밖 이동 금지(외부 리소스 GET은 허용) | 다른 사이트 접근 |
| 6 | 능동 시험 격리: 승인 항목의 정확한 URL·메서드만 잠시 허용, 끝나면 자동 원복 | 승인 범위 밖 시험 |

### 7-2. 개인정보·자격증명

- 로그인 단계에는 write_guard·HAR 기록을 끄고, 로그인 뒤에 켠다(로그인 요청 본문의 비밀번호를 남기지 않기 위해).
- 능동 시험 중 HAR은 비밀번호 칸 값과 `password`·`pw`·`passwd` 계열 파라미터를 저장 전에 `***`로 바꾼다.
- 아이디·비밀번호는 채팅·파일·스크립트 인자 어디에도 남기지 않는다.

### 7-3. 사이트 부담

- 단일 탭, 순차 수집, 페이지 사이 1~2초 대기.
- 429·403 연속, WAF 차단 화면, CAPTCHA가 보이면 즉시 멈추고 사용자에게 알린다.

### 7-4. 오류 처리

| 상황 | 처리 |
|---|---|
| 세션 만료 | 멈추고 재로그인 요청, 그 메뉴부터 이어서 수집 |
| 빈 화면(EMPTY) | ready 조건을 고쳐 재수집, 그래도 비면 "데이터 없음 상태로 점검" 기록 |
| 조회 요청 차단으로 화면 깨짐 | 막힌 요청 목록을 보여주고 사용자가 허용 여부 결정 |
| 메뉴 접근 불가(권한·404) | 커버리지에 접근 불가와 사유, 해당 항목은 점검불가 |
| 중간 끊김 | 단계별 파일 기준으로 끊긴 단계부터 재개 |
| 가림 누락·과잉 | 미리보기 육안 확인, 좌표 수동 지정 후 재확인 |

## 8. 검증

### 8-1. 데모 사이트 `demo/`

localhost 웹앱. 다음을 넣는다.
- 관찰 항목을 고루 포함한 취약점 약 20개와 정답표 `expected.json`(기대 판정·기준 ID). 능동 시험 항목 1개 이상(인증 실패 제한 없음).
- 함정: 저장 POST, 삭제 GET 링크, 로그아웃 링크, sendBeacon, WebSocket 송신. 서버는 받은 쓰기 요청을 모두 로그에 남긴다.
- 가짜 개인정보(가림 검사용).

### 8-2. 단위 테스트(TDD)

write_guard(메서드별 차단, 허용 목록, WebSocket·beacon, 잠시 허용·원복), GET 금지 목록, HAR 정제, auto_checks 탐지기별 양성·음성, findings 정렬·번호·박스-문제점 불일치 경고, mask(픽셀화 적용·박스 그리기), report 빌더(페이지 생성·목차 순서·해시 이동).

### 8-3. 처음부터 끝까지(데모 대상)

- 데모 서버 쓰기 로그 0건(승인한 능동 시험 요청 제외).
- 정답표의 관찰 항목 전부 탐지, 안전 화면 오탐 0.
- 리포트 이미지에 가짜 개인정보가 보이지 않음(원본 크기 육안 확인).

### 8-4. 리포트 검증

- `verify_report.py`: 콘솔 오류, 모든 상세 페이지 표시·이미지 로딩, 목차 이동, 이전·다음, 인쇄 쪽 나눔, 모바일 넘침. 종료코드 0.
- 증거 png 육안 검수: 개요, 상세 몇 쪽, 확대 보기, 인쇄 쪽.

### 8-5. 최종 인수

데모를 통과한 뒤, 사용자가 승인한 실제 대상(staging 권장)에서 시범 점검 1회. 메뉴 구조, 조회성 POST 패턴, 가림 누락처럼 데모로 확인할 수 없는 부분을 본다.

## 9. 남은 확인 사항

설계 승인과 별개로 구현 중에 정한다. 상세는 [docs/reference/criteria/README.md](../reference/criteria/README.md)의 "확인·결정이 필요한 점".

1. 시행일: 안내서가 2026.10.31.~11.1. 시행으로 적은 조항(제4조①12·13호, 제5조①⑥, 제6조②, 제8조 개정분)의 현행 적용 여부를 원문으로 확인.
2. 원문에 없는 별표·위임 고시(고시 별표, 영 별표 1·6, 「개인정보 처리 방법에 관한 고시」 등) 확보.
3. 점검 기준 YAML 변환 후 `strength`·`default_risk` 1차 값의 사용자 확인.
4. 범위 밖 후보(망법 콘텐츠 규제, 영상정보처리기기, 공공기관 파일 등록)를 일괄 해당없음으로 둘지.
5. 체크박스 해제 후 진행 버튼 활성 여부 관찰을 "관찰"로 허용할지(제출은 하지 않음).
6. 6-3 권고 기준값(특히 세션 30분, 실패 5회)은 설계 단계에서 Claude가 제안한 값이다. 설계서 승인 시 함께 확인한다.
