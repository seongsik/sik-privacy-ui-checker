## 제7조 개인정보의 암호화

### SAFE-07-01-01 인증정보(비밀번호) 전송 구간 암호화
- 근거: 고시 제7조제1항; 고시 제7조제4항; 안내서 p.82(송·수신 시 SSL/TLS 등), p.87; 안내서 부록 FAQ 6-3·6-4(p.145~146)
- 요구사항: 비밀번호·생체인식정보 등 인증정보를 정보통신망으로 송·수신할 때는 안전한 암호 알고리즘으로 암호화해야 한다. 내부망도 포함된다. 방법은 SSL/TLS 같은 통신구간 암호화나 응용프로그램 암호화 전송이다. 전용선은 구간 암호화를 대신하지 못한다(FAQ 6-4).
- 적용조건: 모든 개인정보처리자. 정보주체(이용자)와 개인정보취급자(관리자)의 인증 모두 해당한다.
- 점검유형: 관찰
- 점검위치: 로그인 화면, 회원가입, 비밀번호 변경, 비밀번호 찾기·재설정, 본인확인(재인증) 화면, 관리자 로그인 화면
- 점검방법:
  1. 화면 URL의 스킴을 확인한다(`location.protocol`).
  2. 읽기 전용 JS로 비밀번호 칸이 속한 form을 조회한다: `[...document.querySelectorAll('input[type=password]')].map(i=>({form:i.form?.action, method:i.form?.method}))`. action이 `http://`로 시작하는지, 상대경로이면 현재 스킴이 https인지 본다.
  3. 사용자가 직접 로그인한 뒤 네트워크 요청 목록에서 로그인 요청의 URL 스킴(https 여부), 메서드, 대상 호스트를 확인한다. 응답이 리다이렉트이면 중간 hop에 http가 있는지도 본다.
  4. AJAX 로그인이면 JS 번들에서 로그인 API 주소가 `http://`로 하드코딩되어 있는지 찾는다.
  5. 요청 본문의 비밀번호 값이 평문으로 보이더라도 https 구간이면 양호다. 다만 응용 계층 "암호화"라고 하면서 실제로는 Base64 인코딩만 한 것은 암호화로 보지 않고 기록한다.
  6. `http://` 주소로 직접 GET 이동해 로그인 화면이 http로 그대로 열리는지, https로 리다이렉트되는지 확인한다.
- 양호기준: 인증정보를 보내는 모든 요청이 https(TLS)로 전송되고, http 접근은 https로 강제 전환된다.
- 취약기준: 로그인·가입·비밀번호 변경 요청 가운데 하나라도 평문 http로 전송된다. 로그인 화면이 http로 열리고 그 상태로 제출할 수 있다. form action이 http 주소다.
- 조치방안:
  - 전 구간 HTTPS를 적용한다. 웹서버에서 80→443 영구 리다이렉트(301/308)를 설정한다.
  - form action과 API base URL을 https 또는 스킴 상대가 아닌 절대 https로 고친다.
  - HSTS(`Strict-Transport-Security: max-age=31536000; includeSubDomains`)를 적용한다. 이 값은 점검자 권고이며 안내서 수치가 아니다.
  - 응용 계층 암호화를 쓴다면 안내서 p.83 권고 알고리즘(예: RSAES-OAEP 2048비트 이상)을 쓰고 인코딩만 하는 방식은 폐기한다.
  - 관리적으로는 내부 관리계획의 암호화 항목에 "인증정보 전송 시 TLS 필수"를 명시한다.
- 증적: 로그인 요청의 네트워크 항목(URL·메서드·스킴) 캡처, form action/method 조회 결과, http 접근 시 리다이렉트 여부 캡처. 요청 본문에 비밀번호가 찍히면 반드시 마스킹한다(사용자가 입력한 값이므로 증적에 남기지 않는다).
- 비고: 법령 의무(제7조제1항·제4항)다. FAQ 6-3에 따르면 송신 전에 이미 안전하게 암호화되어 도용·재사용 위험이 없으면 구간 암호화를 추가로 할 필요가 없다. 다만 일방향 암호화 값 자체가 인증정보로 쓰이면(예: 클라이언트 해시를 그대로 서버 인증에 쓰는 경우) 그 값도 구간 암호화가 필요하다. 클라이언트 해시만 하고 http로 보내는 방식은 취약으로 본다. HTTPS 전반은 SAFE-07-04-01과 함께 판정한다.

### SAFE-07-01-02 비밀번호의 URL·GET 파라미터 노출
- 근거: 고시 제7조제1항; 고시 제2조제8호(비밀번호는 타인에게 공개되지 않는 정보); 안내서 p.82
- 요구사항: 인증정보는 암호화하여 송·수신해야 한다. URL 쿼리스트링에 실린 비밀번호는 TLS 안에서도 브라우저 기록, 서버·프록시 로그, Referer 헤더에 평문으로 남는다. 안전한 송·수신 요건을 충족하지 못하는 것으로 본다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 관찰
- 점검위치: 로그인, 비밀번호 변경, 비밀번호 찾기·재설정, 본인확인, 관리자 로그인, 임시비밀번호 발급 링크
- 점검방법:
  1. 비밀번호 칸이 있는 form의 method를 확인한다(`form.method`). GET이면 기록한다.
  2. 사용자가 로그인할 때 네트워크 요청 URL의 쿼리스트링에 `pw`, `pwd`, `passwd`, `password`, `userPw`, `pass`, `secret` 등의 파라미터가 있는지 본다.
  3. 로그인 뒤 리다이렉트 URL과 `location.href`, `history`에 비밀번호나 토큰이 남는지 본다.
  4. 비밀번호 재설정 메일 링크 형식이 화면 안내에 있으면 일회성 토큰인지 비밀번호 자체인지 확인한다.
- 양호기준: 비밀번호는 POST 본문(또는 응용 암호화된 본문)으로만 전송되고 URL에는 나타나지 않는다.
- 취약기준: 비밀번호(또는 임시비밀번호)가 URL 경로나 쿼리 파라미터에 실린다. 비밀번호 칸이 있는 form이 GET 방식이다.
- 조치방안:
  - form method를 POST로 바꾸고 서버에서 GET 요청의 인증 파라미터를 거부한다.
  - 비밀번호 재설정은 비밀번호가 아니라 일회성·만료형 토큰 링크로 처리한다. 이는 점검자 권고다.
  - `Referrer-Policy: strict-origin-when-cross-origin` 이상을 적용하고, 서버·WAF 로그에서 해당 파라미터를 마스킹한다.
- 증적: 해당 요청 URL 캡처(비밀번호 값은 마스킹), form 속성 조회 결과
- 비고: 고시에 "URL 금지"라는 명문은 없고, 제7조제1항의 해석으로 판정한다. 보고서에는 "법령 해석에 따른 취약"이라고 적는다.

### SAFE-07-01-03 접근토큰 등 기타 인증정보의 전송·브라우저 저장
- 근거: 고시 제7조제1항; 고시 제2조제11호(인증정보); 안내서 p.82(비밀번호 외 인증정보도 암호화, API Access Key는 비밀번호로 보지 않으나 안전한 관리 필요); 안내서 부록 FAQ 6-5(p.146)
- 요구사항: 접근토큰(Access Token), 갱신토큰(Refresh Token), 비밀접근키(Secret Access Key) 등 인증정보에 해당하면 저장·송수신 시 암호화해야 한다. 시스템 구성에 따른 인증정보를 명확히 식별해 안전조치를 해야 한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 관찰
- 점검위치: 로그인 직후 전 화면, 마이페이지, 관리자 화면
- 점검방법:
  1. 토큰이 실린 요청이 모두 https인지 확인한다(네트워크 목록).
  2. 토큰이 URL 쿼리(`?token=`, `access_token=`, `jsessionid=`)에 실리는지 확인한다.
  3. 읽기 전용 JS로 `document.cookie`를 조회한다. 세션 쿠키·토큰이 보이면 HttpOnly가 미설정된 것이다.
  4. `Object.keys(localStorage)`, `Object.keys(sessionStorage)`에서 `token`, `jwt`, `refresh`, `secret`, `apiKey` 등 키를 찾는다. 값은 앞 몇 글자만 기록한다.
  5. JS 번들과 페이지 소스에서 `secretKey`, `clientSecret`, `AKIA` 같은 하드코딩된 비밀키를 찾는다.
  6. 쿠키 Secure 속성은 JS로 확인할 수 없으므로, 응답 헤더를 볼 수 있으면 `Set-Cookie` 속성을 확인하고, 볼 수 없으면 "확인불가"로 남긴다.
- 양호기준: 토큰이 https로만 전송되고 URL에 실리지 않는다. 세션 쿠키에 HttpOnly·Secure가 설정되어 있다. 갱신토큰·비밀키가 브라우저 저장소나 JS 소스에 평문으로 남지 않는다.
- 취약기준: 토큰·세션ID가 http로 전송되거나 URL에 실린다. 비밀접근키·클라이언트 시크릿이 프런트 소스에 노출된다.
- 주의(추가 확인 필요): 갱신토큰을 localStorage에 장기 보관하는 것은 "주의"로 기록한다. 법령상 명시 금지는 아니다.
- 조치방안:
  - 세션·갱신토큰은 `Set-Cookie: ...; Secure; HttpOnly; SameSite=Lax`(또는 Strict) 쿠키로 옮긴다.
  - 접근토큰은 짧은 만료로 메모리에만 보관한다.
  - URL 토큰 전달(세션 ID URL rewriting 등)을 비활성화한다.
  - 클라이언트에 노출된 비밀키는 즉시 폐기·재발급하고 서버측 프록시로 옮긴다.
  - 이상의 설정 예시는 점검자 권고다. 안내서 근거는 FAQ 6-5의 "인증정보 식별 및 암호화"다.
- 증적: 저장소 키 목록, 쿠키 이름 목록(값은 마스킹), 토큰이 실린 요청 URL(값 마스킹), 소스 내 노출 위치(파일명·행)
- 비고: 안내서는 토큰 등이 "인증정보에 해당한다면" 암호화 대상이라고 한다(FAQ 6-5). 저장 위치에 대한 구체 기준은 없다. HttpOnly·SameSite는 접근통제(제6조) 쪽 항목과 겹칠 수 있으니 통합 시 조정한다.

### SAFE-07-01-04 응답·화면·브라우저 저장소의 비밀번호 노출
- 근거: 고시 제7조제1항 단서(비밀번호는 일방향 암호화 저장); 안내서 p.82(일방향 암호화 = 해시함수 등으로 비가역 저장)
- 요구사항: 비밀번호는 복호화되지 않도록 일방향 암호화하여 저장해야 한다. 서버가 평문 비밀번호를 되돌려 줄 수 있다면 일방향 암호화가 적용되지 않았다는 정황이다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 관찰. 비밀번호 찾기 실제 실행은 능동(승인).
- 점검위치: 마이페이지(회원정보 수정), 비밀번호 변경, 비밀번호 찾기 결과 화면, 관리자 회원 상세 화면, 관리자 계정 관리 화면
- 점검방법:
  1. 회원정보 수정 화면에서 비밀번호 칸에 값이 미리 채워져 있는지 확인한다: `[...document.querySelectorAll('input[type=password]')].map(i=>i.value.length)`. 길이만 기록하고 값은 읽지 않는다.
  2. 마이페이지·회원정보 API 응답 본문(JSON)에 `password`, `pwd`, `passwd`, `userPw` 필드가 있는지, 값이 평문인지 해시인지 확인한다.
  3. 관리자 회원 상세 화면과 API 응답에 회원 비밀번호(평문 또는 해시) 필드가 있는지 확인한다.
  4. `localStorage`, `sessionStorage`, 전역 JS 변수(`window` 객체의 user·member 객체)에 비밀번호 필드가 있는지 확인한다.
  5. 비밀번호 찾기가 "기존 비밀번호 안내" 방식인지 "임시비밀번호·재설정 링크" 방식인지 화면 안내 문구로 확인한다. 실제 실행은 메일·문자를 발송하므로 사용자 승인 후 테스트 계정으로만 하고, 입력은 사용자가 한다.
- 양호기준: 어떤 화면·응답·저장소에도 비밀번호 평문이 나타나지 않는다. 비밀번호 찾기는 재설정 방식이다.
- 취약기준: 다음 중 하나라도 해당하면 취약이다.
  - 응답·화면·저장소에 비밀번호 평문이 있다.
  - 비밀번호 칸에 저장된 비밀번호가 채워진다.
  - 비밀번호 찾기가 기존 비밀번호를 그대로 알려준다(복호화 가능 저장의 강한 정황).
- 주의(추가 확인 필요): 응답에 비밀번호 해시값이 포함되면 "주의(불필요한 인증정보 노출)"로 기록한다.
- 조치방안:
  - 비밀번호를 응답 DTO와 화면 모델에서 제거한다(직렬화 제외).
  - 회원정보 수정 화면은 "현재 비밀번호 확인 + 새 비밀번호" 입력 방식으로 바꾼다.
  - 비밀번호 찾기는 본인확인 뒤 재설정 링크나 임시비밀번호를 발급하고 최초 로그인 시 변경을 강제한다.
  - 저장 방식을 일방향 해시(SHA-256 이상 + 솔트)로 전환한다(SAFE-07-01-05).
- 증적: 해당 응답의 필드명 목록 캡처(값은 반드시 마스킹), 화면 캡처(비밀번호 칸 값 마스킹), 비밀번호 찾기 안내 문구 캡처
- 비고: 저장 방식 자체는 서면 항목(SAFE-07-01-05)으로 확인하고, 이 항목은 그 정황 증거다. 평문 노출이 확인되면 서면 확인 결과와 관계없이 취약으로 판정한다.

### SAFE-07-01-05 비밀번호 일방향 암호화 저장
- 근거: 고시 제7조제1항 단서; 안내서 p.82(솔트값, 무작위 대입·레인보우 테이블 대응), p.83(권고 알고리즘 표), p.85(DMZ 저장 시 인증정보 암호화)
- 요구사항: 비밀번호는 복호화되지 않도록 일방향 암호화(해시)하여 저장해야 한다. 무작위 대입공격과 레인보우 테이블 공격에 대응하는 조치를 해야 하며, 솔트 추가를 고려한다. 권고 알고리즘은 SHA-224/256/384/512 등이고, MD5와 SHA-1은 사용 금지다.
- 적용조건: 모든 개인정보처리자. 이용자와 개인정보취급자 비밀번호 모두 해당한다.
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 다음을 요청한다.
  - 회원·관리자 계정 테이블 정의서
  - 비밀번호 저장 로직 소스 또는 설계서(해시 알고리즘, 솔트 사용 여부, 반복 횟수)
  - DB 샘플 캡처(해시 형식만, 마스킹)
  - 내부 관리계획의 암호화 조항
- 양호기준: SHA-256 이상 일방향 해시에 솔트를 적용해 저장한다. 키 스트레칭 함수(PBKDF2, bcrypt, scrypt, Argon2)를 쓰는 경우도 양호다.
- 취약기준: 평문 저장, 양방향 암호화(AES 등) 저장, MD5·SHA-1 해시 저장
- 주의(추가 확인 필요): 솔트 없이 단순 해시만 하는 경우는 "주의"로 기록한다.
- 조치방안:
  - 로그인 시점 재해시(lazy migration)나 일괄 비밀번호 재설정으로 저장 방식을 전환한다.
  - 알고리즘은 안내서 p.83 표의 SHA-2 계열을 쓰고 사용자별 무작위 솔트를 적용한다.
  - 가능하면 PBKDF2·bcrypt·Argon2 같은 키 스트레칭을 쓴다. 이는 점검자 권고다.
  - 내부 관리계획에 알고리즘과 솔트 정책을 명시한다.
- 증적: 서면 자료 사본, 담당자 확인 기록
- 비고: 법령 의무다. 솔트는 안내서상 "고려할 필요"이므로 권고 수준이다. MD5·SHA-1 금지는 안내서 p.83의 명시 사항이다. SAFE-07-01-04에서 평문 노출 정황이 나오면 함께 기재한다.

### SAFE-07-01-06 비밀번호 외 인증정보 저장 암호화
- 근거: 고시 제7조제1항 본문; 고시 제7조제2항제7호(생체인식정보); 안내서 p.82, p.84~85; FAQ 6-5(p.146)
- 요구사항: 생체인식정보, 접근토큰, 비밀접근키 등 인증정보를 DB·파일로 저장할 때는 안전한 암호 알고리즘으로 암호화해야 한다. 비밀번호가 아니므로 양방향 암호화도 허용된다. API Access Key는 비밀번호로 보지 않지만 안전한 관리방안을 세워야 한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 다음을 요청한다.
  - 인증정보 식별 목록(생체 템플릿, 토큰, API 키, OTP 시드 등)과 각 저장 위치·암호화 방식
  - 설정 파일 내 비밀키 저장 방식(평문 여부)
- 양호기준: 식별된 모든 인증정보가 권고 알고리즘(AES-128 이상, ARIA, SEED, LEA 등)으로 암호화되어 저장된다.
- 취약기준: 생체 템플릿·토큰·API 비밀키가 평문으로 DB·설정파일에 저장된다.
- 조치방안:
  - 인증정보 인벤토리를 작성한다.
  - DB 컬럼 암호화나 비밀관리 서비스(KMS, Vault 등)로 이전한다.
  - 설정 파일의 평문 키를 제거하고 환경변수나 비밀저장소를 참조하게 한다.
  - 내부 관리계획에 인증정보 관리방안을 추가한다(안내서 p.82 "안전한 관리방안 수립").
- 증적: 인벤토리, 암호화 설정 캡처
- 비고: 법령 의무다. API Access Key는 안내서상 "비밀번호로 간주하지 않음"이므로 일방향 암호화 의무는 없다.

### SAFE-07-02-01 이용자 고유식별정보·카드·계좌·생체정보 저장 암호화
- 근거: 고시 제7조제2항제1~7호; 「개인정보 보호법」 제24조의2제2항; 시행령 제21조의2; 안내서 p.83~84, p.86(주민등록번호), p.88(적용기준 요약표); FAQ 6-1(p.145)
- 요구사항: 이용자의 주민등록번호, 여권번호, 운전면허번호, 외국인등록번호, 신용카드번호, 계좌번호, 생체인식정보는 안전한 암호 알고리즘으로 암호화하여 저장해야 한다. 저장 위치(인터넷·DMZ·내부망)와 관계없다. 클라우드 제공자의 암호화 기능을 쓸 수 있으나 기준 부합 여부를 확인해야 한다.
- 적용조건: 이용자(정보통신서비스 이용자)의 개인정보를 처리하는 자. 주민등록번호는 이용자 여부와 관계없이 전자적으로 보관하는 모든 개인정보처리자가 대상이다(법 제24조의2).
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 다음을 요청한다.
  - 개인정보파일 목록과 항목별 암호화 현황표
  - DB 컬럼 암호화 설정(알고리즘·키 길이)
  - 클라우드 암호화 기능을 쓰면 그 사양
- 양호기준: 7개 항목 모두 권고 알고리즘(AES-128/192/256, ARIA-128/192/256, SEED, LEA 등)으로 암호화되어 저장된다.
- 취약기준: 하나라도 평문 저장이다. 또는 TDEA(3DES) 등 보안강도가 낮은 알고리즘을 쓴다.
- 조치방안:
  - DB 암호화 솔루션(API형·플러그인형·TDE)으로 컬럼 단위 암호화를 적용한다.
  - 알고리즘은 안내서 p.83 표 범위에서 고른다.
  - 검증필 암호모듈 사용을 검토한다(안내서 p.188 국정원 암호모듈 검증 참고 사이트).
  - 키 관리는 SAFE-07-06-01과 연계한다.
  - 내부 관리계획과 개인정보파일 대장에 암호화 현황을 반영한다.
- 증적: 서면 자료
- 비고: 법령 의무다. 화면이나 응답에 전체 번호가 평문으로 나오는 것은 저장 암호화 위반의 증거가 아니다(복호화 후 표시할 수 있으므로). 노출 자체는 SAFE-12-01-03에서 판정한다.

### SAFE-07-03-01 이용자가 아닌 정보주체의 고유식별정보 저장 암호화
- 근거: 고시 제7조제3항제1·2호; 법 제24조의2; 시행령 제21조의2; 안내서 p.84~86(DMZ 정의·예시, 영향평가·위험도 분석); 부록 제2장 위험도 분석 기준(p.163~); FAQ 6-1(p.145)
- 요구사항: 다음 경우에 암호화한다.
  - 인터넷망 구간이나 DMZ에 고유식별정보를 저장하면 암호화해야 한다.
  - 내부망에 저장하는 경우 주민등록번호는 무조건 암호화한다.
  - 내부망에 저장하는 그 밖의 고유식별정보는 공공기관이면 영향평가 결과, 그 외에는 위험도 분석 결과에 따라 적용 여부와 범위를 정할 수 있다.
- 적용조건: 이용자가 아닌 정보주체(직원, 오프라인 고객 등)의 고유식별정보를 처리하는 자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 다음을 요청한다.
  - 네트워크 구성도(DB의 DMZ·내부망 위치)
  - 고유식별정보 보유 현황
  - 영향평가 결과서 또는 위험도 분석 결과보고서(미암호화 시)
- 양호기준: DMZ·인터넷 구간의 고유식별정보와 내부망의 주민등록번호가 모두 암호화되어 있다. 내부망 미암호화 항목에는 유효한 영향평가·위험도 분석 결과가 있다.
- 취약기준: DMZ에 평문 고유식별정보가 있다. 내부망 주민등록번호가 평문이다. 미암호화 근거 문서가 없다.
- 조치방안:
  - 해당 컬럼을 암호화한다.
  - 미암호화를 유지하려면 부록 제2장 서식에 따라 위험도 분석 결과보고서를 작성하고 보완조치를 이행한다(안내서 예시).
- 증적: 구성도, 분석 결과서
- 비고: 법령 의무다. 웹 점검으로는 DB 위치를 알 수 없다.

### SAFE-07-04-01 개인정보 송·수신 시 HTTPS 적용 범위
- 근거: 고시 제7조제4항; 고시 제7조제1항; 안내서 p.87(SSL 인증서 보안서버, 응용프로그램 암호화); 안내서 p.88 요약표
- 요구사항: 개인정보를 정보통신망을 통해 인터넷망 구간으로 송·수신하면 안전한 암호 알고리즘으로 암호화해야 한다. SSL 인증서 기반 보안서버나 응용프로그램 암호화를 활용할 수 있다.
- 적용조건: 모든 개인정보처리자. 이용자와 비이용자 모두 해당한다.
- 점검유형: 관찰
- 점검위치: 전 화면. 특히 회원가입, 마이페이지, 주문·결제·배송지, 문의·상담 폼, 개인정보 조회·목록 화면, 관리자 화면, 파일 업로드·다운로드
- 점검방법:
  1. 메뉴 탐색 중 방문한 모든 페이지의 `location.protocol`을 기록한다.
  2. 대표 URL(메인, 로그인, 가입, 마이페이지, 관리자)을 `http://`로 직접 열어 https로 301/302/307/308 리다이렉트되는지, http로 그대로 서비스되는지 확인한다.
  3. 개인정보 입력 form의 `action` 스킴을 조회한다: `[...document.forms].map(f=>[f.action,f.method])`.
  4. 네트워크 요청 목록에서 `http://`로 시작하는 XHR·fetch·form 요청을 찾는다. 특히 개인정보를 실은 API를 본다.
  5. 외부 도메인(주소검색, 본인확인, 상담 위젯 등)으로 개인정보가 전송되면 그 요청도 https인지 확인한다.
  6. 서브도메인(admin., m., api.)도 같은 방식으로 확인한다.
  7. 응답 헤더를 확인한다: `await fetch(location.href,{method:'HEAD'}).then(r=>r.headers.get('strict-transport-security'))`. 읽기 전용 동일출처 요청이다.
- 양호기준: 개인정보를 표시하거나 송·수신하는 모든 페이지와 API가 https로만 제공되고 http 접근은 https로 전환된다.
- 취약기준: 개인정보 입력·조회 페이지나 API가 http로 제공·전송된다. http 접근 시 리다이렉트 없이 서비스된다.
- 주의(추가 확인 필요): 개인정보가 없는 페이지만 http이면 "주의"로 기록한다.
- 조치방안:
  - 전 사이트에 TLS 인증서를 적용하고 http→https 영구 리다이렉트를 설정한다. Nginx 예: `return 301 https://$host$request_uri;`
  - HSTS(`max-age=31536000; includeSubDomains`)를 적용한다. 운영 안정화 뒤 preload를 검토한다.
  - 하드코딩된 http API 주소를 수정한다.
  - 외부 연동 업체에도 https 사용을 요구한다(위탁·제공 계약에 반영).
  - 위 설정값은 점검자 권고이고, 안내서는 "SSL 인증서를 이용한 보안서버"까지만 예시한다(p.87).
- 증적: 페이지별 스킴 목록, http 접근 결과 캡처, http 요청 목록(개인정보 값은 마스킹), HSTS 헤더 값
- 비고: 법령 의무다. 현행 고시는 "인터넷망 구간으로 송·수신"을 요건으로 하므로 내부망 전용 관리자 시스템의 일반 개인정보는 제4항 대상이 아니다. 인증정보는 내부망도 제1항 대상이다. HSTS 미적용 자체는 법령 위반이 아니라 권고 사항이므로 "주의"로 둔다.

### SAFE-07-04-02 혼합 콘텐츠(Mixed Content)
- 근거: 고시 제7조제4항; 고시 제7조제1항; 안내서 p.87
- 요구사항: https 페이지가 http 자원을 불러오면 그 구간이 평문이 된다. 스크립트·form·iframe을 http로 받으면 개인정보나 인증정보 입력 화면이 변조·도청될 수 있어 전송 암호화 취지를 훼손한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 관찰
- 점검위치: 전 화면. 특히 로그인, 가입, 결제, 마이페이지, 관리자 화면
- 점검방법:
  1. 콘솔 메시지에서 "Mixed Content" 경고·오류를 수집한다.
  2. DOM에서 http 자원을 찾는다: `[...document.querySelectorAll('[src],[href],form[action],iframe')].map(e=>e.src||e.href||e.action).filter(u=>u&&u.startsWith('http:'))`
  3. `performance.getEntriesByType('resource').filter(r=>r.name.startsWith('http:'))`로 실제 로드된 http 자원을 확인한다.
  4. 결과를 active(script, iframe, form action, XHR)와 passive(img, media)로 구분한다.
- 양호기준: https 페이지에서 http 자원 요청이 없다.
- 취약기준: 개인정보·인증정보를 다루는 페이지에서 active 혼합 콘텐츠(script, iframe, form action, XHR)가 있다.
- 주의(추가 확인 필요): passive 혼합 콘텐츠(이미지 등)만 있으면 "주의"로 기록한다.
- 조치방안:
  - 자원 URL을 https 또는 상대경로로 고친다.
  - `Content-Security-Policy: upgrade-insecure-requests`를 적용한다.
  - https를 지원하지 않는 외부 자원은 자체 호스팅하거나 교체한다.
  - 이상은 점검자 권고다.
- 증적: 콘솔 메시지 캡처, http 자원 목록
- 비고: 고시·안내서에 혼합 콘텐츠라는 용어는 없고, 제7조제1·4항의 해석으로 판정한다.

### SAFE-07-04-03 TLS 설정·인증서·안전한 암호 알고리즘
- 근거: 고시 제7조제1항·제4항("안전한 암호 알고리즘"); 안내서 p.83(사용 권장 알고리즘 표, TDEA·MD5·SHA-1 사용 금지, 최신 정보 확인 필요), p.87; 안내서 부록 제3장(p.188, 국정원 암호모듈 검증 ncsc.go.kr, KISA 암호이용활성화 seed.kisa.or.kr)
- 요구사항: 송·수신 암호화는 국내외 암호 연구기관이 권고하는 안전한 알고리즘을 써야 한다. 보안강도가 낮은 TDEA(3DES), MD5, SHA-1은 쓰면 안 된다.
  - 안내서 p.83 권고 표: 대칭키는 AES·ARIA·LEA·SEED·Camellia, 해시는 SHA-224 이상, 공개키는 RSA(RSAES-OAEP) 2048비트 이상
- 적용조건: 모든 개인정보처리자
- 점검유형: 관찰(부분). 프로토콜 버전·암호군은 별도 도구가 필요하다.
- 점검위치: 서비스 도메인 전체(웹, 모바일웹, API, 관리자 도메인)
- 점검방법:
  1. 브라우저 주소창의 인증서 경고 유무를 확인한다. 인증서 만료, 도메인 불일치, 자체서명 경고를 스크린샷으로 남긴다.
  2. `performance.getEntriesByType('navigation')[0].nextHopProtocol`을 기록한다. `h3`이면 TLS 1.3이고, `h2`이면 실무상 TLS 1.2 이상이다. `http/1.1`이면 판정 불가다.
  3. TLS 버전(1.0/1.1 허용 여부)과 암호군(3DES, RC4, NULL, EXPORT), 인증서 서명 알고리즘(SHA-1)은 브라우저 JS로 확인할 수 없다. 사용자에게 다음을 안내한다.
     - 사용자 PC에서 `openssl s_client -connect <host>:443 -tls1_1` 등을 직접 실행한다.
     - 또는 사용자 승인 하에 외부 진단 서비스를 쓴다. 이 경우 도메인이 제3자에 전달됨을 고지한다.
  4. 그래도 확인하지 못하면 "점검불가(별도 도구 필요)"로 둔다.
- 양호기준: 유효한 신뢰 인증서를 쓰고, 인증서 서명이 SHA-256 이상이며 키가 RSA 2048비트 이상(또는 동등한 ECC)이다. TLS 1.2 이상만 허용하고 3DES·RC4·NULL 암호군이 비활성이다.
- 취약기준: 인증서 오류(만료·불일치·자체서명), SHA-1 서명 인증서, 3DES 등 금지 알고리즘 암호군 허용, SSL 3.0 허용
- 주의(추가 확인 필요): TLS 1.0/1.1 허용은 "취약(점검자 기준)"으로 기록하고 판정 확정은 사용자 결정에 맡긴다.
- 조치방안:
  - 웹서버 TLS 설정을 `ssl_protocols TLSv1.2 TLSv1.3;`으로 하고, 암호군은 AEAD(AES-GCM, CHACHA20) 중심으로 하고 3DES·RC4·NULL·EXPORT를 제외한다.
  - RSA 2048비트 이상·SHA-256 서명 인증서로 교체하고 인증서 만료 모니터링을 도입한다.
  - 버전·암호군 설정 예시는 점검자 권고이고, 금지 알고리즘(3DES, SHA-1)은 안내서 p.83 근거다.
  - 최신 권고는 KISA 암호이용활성화(seed.kisa.or.kr)와 국정원 검증필 암호모듈 목록(ncsc.go.kr)을 확인한다(안내서 p.188).
- 증적: 인증서 정보 캡처, nextHopProtocol 값, 사용자가 제공한 TLS 진단 결과
- 비고: 안내서에는 TLS 버전 수치 기준이 없다. 부록 제3장은 참고 웹사이트 목록뿐이다. "TLS 1.2 이상"은 점검자 기준(업계 일반 권고)이므로 보고서에 "안내서 수치 아님"이라고 표시한다.

### SAFE-07-05-01 개인정보취급자 컴퓨터·모바일·보조저장매체 저장 시 암호화
- 근거: 고시 제7조제5항; 안내서 p.87~88(오피스 암호 설정, 압축파일 암호, 암호화 소프트웨어); FAQ 6-2(p.145)
- 요구사항: 다음 정보를 개인정보취급자의 컴퓨터, 모바일 기기, 보조저장매체에 저장할 때는 안전한 암호 알고리즘으로 암호화한 뒤 저장해야 한다.
  - 이용자의 개인정보(전 항목)
  - 이용자가 아닌 정보주체의 고유식별정보와 생체인식정보
  - 오피스 프로그램의 암호 설정 기능이나 압축 암호를 쓸 수 있다. 다만 그 알고리즘이 안전해야 한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 다음을 요청한다.
  - PC 개인정보 파일 암호화 정책(DRM, 문서암호화 솔루션, 개인정보 검출 솔루션)
  - 모바일 기기 암호화 설정
  - 보조저장매체 암호화(보안 USB) 정책과 점검 기록
- 양호기준: 취급자 PC·매체에 저장된 개인정보 파일이 암호화되어 있고, 이를 정기적으로 점검한 기록이 있다.
- 취약기준: 평문 개인정보 파일 저장을 허용하고 통제 수단이 없다.
- 조치방안:
  - 문서보안(DRM)이나 개인정보 검출·암호화 솔루션을 도입하고 보안 USB 사용을 의무화한다.
  - 오피스 파일 암호 설정과 압축 암호(AES-256)를 사용하도록 지침을 둔다(안내서 예시).
  - 정기 점검과 결과 보고 절차를 마련한다.
- 증적: 서면 자료
- 비고: 법령 의무다. 다운로드 파일 자체의 암호화 여부는 SAFE-07-05-03에서 확인한다.

### SAFE-07-05-02 관리자 화면의 브라우저 저장소·캐시 내 개인정보 평문 저장
- 근거: 고시 제7조제5항(개인정보취급자 컴퓨터에 저장 시 암호화); 고시 제12조제1항; 안내서 p.87~88
- 요구사항: 관리자(개인정보취급자) 웹 화면이 이용자 개인정보를 취급자 PC의 브라우저 저장소(localStorage, IndexedDB, 장기 쿠키)에 평문으로 남기면, 취급자 컴퓨터에 암호화 없이 저장하는 것에 해당할 수 있다.
- 적용조건: 이용자 개인정보를 웹 관리자 화면으로 처리하는 자
- 점검유형: 관찰
- 점검위치: 관리자 화면(회원 목록·상세, 주문·배송 관리, 상담 관리)
- 점검방법:
  1. 관리자 화면 탐색 뒤 `Object.entries(localStorage)`, `Object.entries(sessionStorage)`의 키 이름과 값 길이를 조회한다.
  2. 값에서 이름·전화번호·이메일·주소·생년월일·주민번호 패턴(`\d{6}-?[1-4]\d{6}`), 카드번호 패턴(`\d{4}-?\d{4}-?\d{4}-?\d{4}`), 계좌번호 형태를 정규식으로 찾는다. 결과는 패턴 일치 건수만 기록한다.
  3. `indexedDB.databases()`로 DB 목록을 확인한다.
  4. 이용자 화면(마이페이지)도 같은 방식으로 보되, 이용자 본인 PC는 제7조제5항 대상이 아니다. 그 결과는 SAFE-12-01-03에 기록한다.
- 양호기준: 관리자 화면이 브라우저 영구 저장소에 이용자 개인정보를 남기지 않는다. 남겨야 하면 암호화된 값만 남긴다.
- 취약기준: localStorage나 IndexedDB에 회원 목록·상세 정보가 평문으로 남는다.
- 주의(추가 확인 필요): 개인정보가 sessionStorage에만 있으면 "주의"로 기록한다(탭 종료 시 삭제되기 때문).
- 조치방안:
  - 개인정보 응답을 메모리 상태로만 유지하고 영구 저장소 캐싱을 제거한다.
  - 필요하면 식별 키만 저장한다.
  - 민감 응답에 `Cache-Control: no-store`를 적용하고 로그아웃 시 저장소를 비운다.
  - 이상은 점검자 권고다.
- 증적: 저장소 키 이름 목록과 패턴 일치 건수. 실제 값은 저장하지 않거나 마스킹한다.
- 비고: 고시가 브라우저 저장소를 명시하지는 않으며, 제7조제5항을 적용한 해석이다. 판정 시 "법령 해석"으로 표시한다.

### SAFE-07-05-03 개인정보 다운로드 파일의 암호화
- 근거: 고시 제7조제5항; 안내서 p.88(내려받아 저장하는 경우 암호화 소프트웨어, 오피스·압축 암호 설정)
- 요구사항: 개인정보처리시스템에서 취급자 PC로 내려받은 개인정보 파일은 암호화하여 저장해야 한다.
- 적용조건: 개인정보 다운로드 기능을 제공하는 자
- 점검유형: 능동(승인)
- 점검위치: 관리자 화면의 엑셀·CSV·PDF 다운로드 기능
- 점검방법:
  1. 다운로드 버튼과 옵션 화면에 "파일 암호 설정", "암호화 다운로드" 같은 문구나 입력칸이 있는지 화면만 보고 확인한다(관찰).
  2. 실제 다운로드는 파일을 내려받는 행위이고 접속기록에 남는다. 따라서 파일명·건수 범위를 사용자에게 알리고 승인을 받은 뒤, 테스트 데이터나 최소 범위로 사용자가 직접 실행한다.
  3. 내려받은 파일이 열 때 암호를 요구하는지, DRM이 걸려 있는지 사용자가 확인해 알려준다. Claude는 파일 내용을 열람하지 않는다.
- 양호기준: 다운로드 파일에 암호 설정이나 DRM이 강제된다. 또는 PC 단 문서암호화 솔루션이 자동 적용된다(서면으로 확인).
- 취약기준: 개인정보가 담긴 파일이 평문으로 내려받아지고 PC 단 암호화 통제도 없다.
- 조치방안:
  - 다운로드 시 파일 암호 입력을 필수로 하거나 서버에서 AES 암호화 압축을 생성한다. 암호는 별도 경로로 전달한다.
  - DRM 자동 적용을 연동한다.
  - 다운로드 사유 입력과 함께 구현한다(SAFE-12-01-05).
  - 근거는 안내서 p.88 예시다.
- 증적: 다운로드 옵션 화면 캡처, 사용자 확인 결과(파일 내용 캡처 금지)
- 비고: 법령 의무(제7조제5항)다. 다운로드 화면 구현 방식은 안내서 예시 수준이다.

### SAFE-07-06-01 암호 키 관리 절차 수립·시행
- 근거: 고시 제7조제6항; 안내서 p.89~90(라이프사이클별 키 관리 절차 예시)
- 요구사항: 대상 개인정보처리자는 암호화된 개인정보를 안전하게 보관하기 위해 암호 키의 생성, 이용, 보관, 배포, 파기 절차를 수립·시행해야 한다. 안내서는 다음 4단계 예시를 든다.
  - 준비: 안전한 난수발생기(RNG)로 키를 생성한다.
  - 운영: 키를 백업·복구할 수 있게 하고, 노출되거나 유효기간이 끝나면 교체한다.
  - 정지: 운영 데이터와 분리해 보관하고, 소스 프로그램에 평문으로 저장하지 않는다.
  - 폐기: 키 자료를 삭제한다.
- 적용조건: 10만명 이상 정보주체를 처리하는 대기업·중견기업·공공기관, 또는 100만명 이상 정보주체를 처리하는 중소기업·단체
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 다음을 요청한다.
  - 암호 키 관리 지침과 절차서
  - 키 보관 방식(HSM, KMS 등)
  - 키 교체·폐기 기록
  - 키 접근권한자 목록
- 양호기준: 문서화된 절차가 있고 실제 이행 기록이 있다.
- 취약기준: 절차가 없다. 키가 소스코드나 설정파일에 평문으로 저장된다. 키 교체·폐기 이력이 없다.
- 조치방안:
  - 안내서 p.89~90의 4단계 예시에 따라 키 관리 절차서를 작성한다.
  - KMS나 HSM을 도입하고, 키 접근권한 분리와 교체 주기를 정한다.
  - 내부 관리계획 암호화 항목에 반영한다.
- 증적: 서면 자료
- 비고: 법령 의무지만 적용조건이 있다. 규모 판단에 쓸 정보주체 수는 사용자에게 확인한다.

### SAFE-07-06-02 클라이언트 측 암호 키·비밀값 노출
- 근거: 고시 제7조제6항; 고시 제7조제1항; 안내서 p.90("암호 키는 응용프로그램의 소스 프로그램 내에 평문으로 저장 금지")
- 요구사항: 암호 키는 소스 프로그램에 평문으로 저장하면 안 된다(안내서 예시). 웹 프런트 JS에 개인정보 암·복호화 키가 들어 있으면 누구나 키를 얻을 수 있어 암호화가 무력화된다.
- 적용조건: 모든 개인정보처리자. 제7조제6항 절차 의무 자체는 규모 조건이 있다.
- 점검유형: 관찰
- 점검위치: 전 화면의 JS 번들, 인라인 스크립트
- 점검방법:
  1. 로드된 스크립트 목록(`performance.getEntriesByType('resource')`의 script)을 읽는다.
  2. 다음 패턴을 찾는다.
     - 암호 라이브러리 호출부(`CryptoJS.AES.encrypt(`, `crypto.subtle.importKey(`, `AES_KEY`, `secretKey`, `encKey`, `iv:`)
     - 하드코딩된 16·24·32바이트 문자열 키
     - `privateKey`, `-----BEGIN RSA PRIVATE KEY-----`
  3. 소스맵(`.map`) 공개 여부도 확인한다(GET만).
- 양호기준: 프런트에 대칭키나 개인키가 없다. 클라이언트 암호화는 서버 공개키(RSA-OAEP 등)만 쓴다.
- 취약기준: 개인정보나 인증정보 암·복호화용 대칭키나 개인키가 JS에 하드코딩되어 있다.
- 조치방안:
  - 키를 프런트에서 제거하고 서버 측 암·복호화로 전환한다.
  - 클라이언트 암호화가 필요하면 서버 공개키만 배포한다.
  - 노출된 키로 암호화된 데이터는 새 키로 재암호화한다.
  - 운영 환경에서 소스맵 공개를 차단한다.
- 증적: 해당 스크립트 URL과 위치(키 값은 일부만 표시)
- 비고: 안내서 키 관리 예시(p.90)를 웹에 적용한 해석이다.

## 제8조 접속기록의 보관 및 점검

### SAFE-08-01-01 접속기록 보관기간(1년·2년)
- 근거: 고시 제8조제1항 각 호; 안내서 p.91~92, p.94(최소 기간 이후 보관기간 설정); FAQ 7-5(p.148)
- 요구사항: 개인정보처리시스템에 접속한 자(정보주체 제외)의 접속기록을 1년 이상 보관·관리한다. 다음에 해당하면 2년 이상 보관한다.
  - 5만명 이상 정보주체를 처리하는 시스템
  - 고유식별정보나 민감정보를 처리하는 시스템
  - 기간통신사업자
  - 오픈마켓 판매자 등 제3자 계정 접속도 포함한다. 처리 목적을 달성해 개인정보를 파기해도 접속기록은 정해진 기간 보관해야 한다.
- 적용조건: 모든 개인정보처리자. 2년 요건은 위 각 호에 해당하는 경우다.
- 점검유형: 서면
- 점검위치: (관찰 보조) 관리자 화면의 접속기록 조회 메뉴
- 점검방법:
  - 서면 확인: 접속기록 보관 정책, 실제 최고(最古) 보관분 조회 결과, 시스템별 해당 호(5만명, 고유식별·민감정보) 판단 자료를 요청한다.
  - 관리자 화면에 접속기록 조회 메뉴가 있으면 조회 가능한 최초 일자를 화면으로 확인한다. 기록 내용 중 개인정보는 마스킹한다.
- 양호기준: 해당 기간 이상의 기록이 실제로 존재한다.
- 취약기준: 보관 기간이 미달한다. 일부 시스템이나 제3자 계정의 기록이 없다.
- 조치방안:
  - 로그 보관 정책을 해당 기간 이상으로 설정하고 별도 저장소로 아카이빙한다.
  - 내부 관리계획에 시스템별 보관기간을 명시한다. 안내서 p.94는 최소기간 이후에도 책임추적에 충분한 기간을 정하도록 권고한다.
- 증적: 서면 자료, 조회 화면 캡처(마스킹)
- 비고: 법령 의무다.
  - 시행시기: 안내서 p.91은 2년 요건을 "'26.11.1 부 시행"으로 적는다(고시 제2025-9호 부칙, 발령 1년 후).
  - 오늘(2026-10-27)은 시행 전이다. 2026.11.1. 이후 점검분부터 2년 기준을 적용한다.
  - 현행 고시 제2026-9호 부칙은 이 유예를 따로 언급하지 않는다. 메모 참조.

### SAFE-08-01-02 접속기록 필수 기록 항목
- 근거: 고시 제2조제3호; 고시 제8조제1항; 안내서 p.92~93(필수 항목과 예시, 쿼리 기록, 가명정보); FAQ 7-1(p.147); 안내서 p.128~129(누락 사례)
- 요구사항: 다음 5개 항목을 모두 기록해야 한다.
  - 식별자
  - 접속일시(년-월-일 시:분:초)
  - 접속지 정보(IP 등)
  - 처리한 정보주체 정보(ID, 고객번호 등)
  - 수행업무(검색, 열람, 조회, 입력, 수정, 삭제, 출력, 다운로드)

  로그인, 로그아웃, 로그인 실패도 기록한다. 처리한 정보주체 정보에는 민감하거나 과도한 개인정보를 남기지 않고, 필요하면 암호화한다. 대량 조회는 쿼리를 기록할 수 있으며 책임추적성 확보 조치가 필요하다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: (관찰 보조) 관리자 접속기록 조회 화면
- 점검방법:
  - 서면 확인: 접속기록 샘플(마스킹)과 로그 스키마를 요청한다.
  - 관리자 화면에 접속기록 메뉴가 있으면 컬럼 구성을 화면으로 확인한다.
  - 점검자가 관리자 화면에서 조회·다운로드한 행위가 기록되었는지 사용자에게 확인을 요청한다. 누락 사례의 예: 신규 메뉴 미연계, 목록 일괄 조회 시 정보주체 공란, 첫 화면 자동 조회 미기록.
- 양호기준: 5개 항목과 로그인·로그아웃·실패 기록이 모든 메뉴에서 생성된다.
- 취약기준: 다음 중 하나라도 해당하면 취약이다.
  - 항목이 누락된다.
  - 일부 메뉴·기능에서 기록이 생성되지 않는다.
  - 목록 조회 시 정보주체가 공란이다.
  - 접속기록에 과도한 개인정보(예: 주민번호 전체)가 평문으로 남는다.
- 조치방안:
  - 공통 로깅 모듈에 모든 개인정보 메뉴를 연계한다.
  - 목록·일괄 조회 시 대상 식별자 목록이나 쿼리, 당시 DB 스냅샷을 기록한다(안내서 p.93 예시).
  - 로그의 정보주체 정보를 식별자 수준으로 최소화한다.
- 증적: 서면 샘플, 화면 캡처(마스킹)
- 비고: 법령 의무다. 이용자 접속기록은 이 기준 대상이 아니다. 다만 「통신비밀보호법」상 3개월 보관이 필요하다(FAQ 7-2, 참고용).

### SAFE-08-02-01 접속기록·다운로드 점검 주기·방법·사후조치
- 근거: 고시 제8조제2항; 안내서 p.94~95(관리항목 표, 비정상 행위 예시, 별도 부서 점검); FAQ 7-4·7-6(p.148~149)
- 요구사항: 접속기록과 개인정보 다운로드 상황을 확인·점검하는 주기, 방법, 사후조치 절차 등을 내부 관리계획으로 정하고 이행해야 한다. 안내서 예시는 다음과 같다.
  - 주기: 실시간, 매일, 매주, 매월, 격월, 분기
  - 방법: 자동화, 스크립트, 수동
  - 점검기준: 비인가 접속, 단시간 대량 다운로드, 업무시간 외 조회 등
  - 사후조치: 보고, 소명, 회수·파기
  - 점검은 취급부서가 아닌 총괄·감사 부서가 하도록 권고한다. 최종 책임은 개인정보 보호책임자에게 있다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 내부 관리계획의 해당 조항, 최근 점검 결과 보고서, 이상행위 소명·조치 기록, 다운로드 현황 점검 기록을 요청한다.
- 양호기준: 주기·방법·기준·사후조치가 규정되어 있고 그대로 이행된 기록이 있다. 다운로드 점검이 포함된다.
- 취약기준: 규정이 없거나 이행 기록이 없다. 다운로드 점검이 빠져 있다. 주기가 과도하게 길다(FAQ 7-6).
- 조치방안:
  - 안내서 p.94 표에 따라 주기·방법·점검기준·사후조치를 내부 관리계획에 규정한다.
  - 비정상 행위 탐지 기준을 수립한다. 안내서 예시는 업무시간 외 접속, 다수 IP, 대량 다운로드다.
  - 점검 결과를 개인정보 보호책임자에게 보고하는 체계를 둔다.
- 증적: 서면 자료
- 비고: 법령 의무다. 안내서 p.94는 "다운로드 상황 점검"을 '26.11.1 시행으로 표시한다(SAFE-08-01-01 비고와 같음).

### SAFE-08-03-01 접속기록 위·변조·도난·분실 방지
- 근거: 고시 제8조제3항; 안내서 p.95(별도 저장장치 백업, WORM, MAC·전자서명 값 별도 보관, 수정·삭제 권한 제한)
- 요구사항: 접속기록이 위·변조, 도난, 분실되지 않도록 안전하게 보관해야 한다. 임의 수정·삭제가 불가능하도록 접근 권한을 제한해야 한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 접속기록 저장 구조(별도 로그서버, WORM), 무결성 검증 방법, 로그 접근권한자 목록, 백업 기록을 요청한다.
- 양호기준: 별도 저장소 백업과 무결성 보장 수단이 있고, 수정·삭제 권한이 제한되어 있다.
- 취약기준: 운영 DB의 같은 테이블에만 있고 관리자가 수정·삭제할 수 있다.
- 조치방안:
  - 로그 서버나 SIEM으로 실시간 전송한다.
  - WORM 스토리지를 쓰거나, 해시·MAC 값을 별도 보관한다(안내서 예시).
  - 로그 삭제 권한을 분리한다.
- 증적: 서면 자료
- 비고: 법령 의무다. 관리자 화면에 "접속기록 삭제" 기능이 보이면 관찰 결과로 첨부한다. 버튼은 누르지 않는다.

## 제9조 악성프로그램 등 방지

### SAFE-09-01-01 보안 프로그램 설치·운영 및 최신 상태 유지
- 근거: 고시 제9조제1항제1호; 안내서 p.96~98(정품 사용, 실시간 감시, 자동 업데이트 또는 일 1회 이상, 업로드 파일 악성코드 검사, 클라우드 기능 활용); FAQ 8-1(p.150)
- 요구사항: 다음 대상에 악성프로그램 방지·치료 보안 프로그램을 설치·운영해야 한다.
  - 개인정보처리시스템(Web, WAS, DBMS)
  - 정보통신망 관리 시스템
  - 업무용 컴퓨터
  - 리눅스 등 비윈도우 OS 포함

  자동 업데이트를 쓰거나 정당한 사유가 없는 한 일 1회 이상 업데이트한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 다음을 요청한다.
  - 백신 설치 현황(서버·PC)
  - 자동·예약 업데이트와 실시간 감시 설정 캡처
  - 라이선스(정품) 증빙
  - 웹 업로드 파일 악성코드 검사 적용 여부
- 양호기준: 대상 전체에 정품 백신이 설치되고, 실시간 감시가 켜져 있으며, 자동 또는 일 1회 이상 업데이트된다.
- 취약기준: 서버(특히 리눅스)에 미설치, 업데이트 지연, 실시간 감시 해제
- 조치방안:
  - 서버용 백신이나 EDR을 도입한다.
  - 중앙관리 콘솔로 업데이트와 정책을 강제한다.
  - 업로드 파일 검사(백신 연동)를 적용한다(안내서 p.97).
- 증적: 서면 자료
- 비고: 법령 의무다. "일 1회 이상"은 고시 수치다. 파일 업로드 기능에 악성 파일을 실제로 올려보는 시험은 운영 데이터 변경이므로 하지 않는다.

### SAFE-09-01-02 발견된 악성프로그램 대응
- 근거: 고시 제9조제1항제2호; 안내서 p.98
- 요구사항: 발견된 악성프로그램은 삭제·치료 등으로 대응해야 한다. 치료가 안 되면 시스템을 분리하는 등 확산 방지 조치를 한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 악성코드 탐지·조치 이력과 대응 절차서를 요청한다.
- 양호기준: 탐지 건별로 조치 기록이 있다.
- 취약기준: 탐지 후 방치했거나 대응 절차가 없다.
- 조치방안: 침해대응 절차(탐지→격리→치료→원인분석→보고)를 문서화하고 이력을 관리한다.
- 증적: 서면 자료
- 비고: 법령 의무다.

### SAFE-09-02-01 보안 업데이트 즉시 적용
- 근거: 고시 제9조제2항; 안내서 p.99("정당한 사유가 없는 한 즉시" = 합리적 소요시간, 형상관리, EOS 확인, KrCERT 보안공지); 부록 위험도 분석 26번(p.185); FAQ 8-1(p.150)
- 요구사항: 악성프로그램 경보가 발령되거나 OS·응용프로그램 제작업체의 보안 업데이트 공지가 있으면 정당한 사유가 없는 한 즉시 업데이트해야 한다. 기술지원 종료(EOS) 여부를 지속적으로 확인해야 한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면. 버전 노출은 관찰 보조.
- 점검위치: 전 화면(응답 헤더, 프런트 라이브러리)
- 점검방법:
  - 서면 확인: 패치 관리 대장(적용 일자), EOS 현황을 요청한다.
  - 관찰 보조 1: `fetch(location.href,{method:'HEAD'})` 응답의 `Server`, `X-Powered-By`, `X-AspNet-Version` 헤더에서 제품·버전 노출을 확인한다.
  - 관찰 보조 2: 프런트 라이브러리 버전(`jQuery.fn.jquery`, `angular.version`, 번들 주석 등)을 기록해 알려진 취약·EOS 버전인지 확인한다.
- 양호기준: 패치가 지체 없이 적용되고, EOS 제품을 쓰지 않거나 대체 조치가 있다.
- 취약기준: 공지 후 장기간 미적용이다. 또는 EOS OS·WAS를 쓴다.
- 주의(추가 확인 필요): 다음은 관찰 근거로 "주의"를 기록하고 서면으로 확정한다.
  - 응답 헤더에서 EOS·구버전 서버 정보가 노출된다.
  - 알려진 고위험 취약 버전의 프런트 라이브러리를 쓴다.
- 조치방안:
  - 패치 관리 절차와 형상관리 대장을 운영한다(안내서 p.99).
  - KrCERT 보안공지(boho.or.kr)를 구독한다.
  - 서버 버전 헤더를 숨긴다(`server_tokens off;`, `X-Powered-By` 제거).
  - 취약 라이브러리를 업그레이드한다. 헤더 숨김은 점검자 권고다.
- 증적: 응답 헤더 값, 라이브러리 버전 목록, 서면 자료
- 비고: 법령 의무는 "업데이트 실시"다. 버전 노출 자체는 법령 위반이 아니므로 정황 증거로만 쓴다.

- 점검위치: -

- 양호기준: 보유 현황을 관리하고, 반출·입을 승인·기록하며, 기술적으로 통제한다.

  - 매체 등록·관리대장을 운영하고 반출·입 승인 절차를 둔다.

## 제12조 출력·복사시 안전조치

### SAFE-12-01-01 출력(화면표시·인쇄·파일생성) 용도 특정과 항목 최소화
- 근거: 고시 제12조제1항; 안내서 p.106(용도별 출력항목 차등, 마스킹, 접근 권한 범위 내 최소 출력); FAQ 10-1(p.152)
- 요구사항: 개인정보를 출력(인쇄, 화면표시, 파일생성 등)할 때는 용도를 특정하고, 용도에 따라 출력 항목을 최소화해야 한다. 업무상 반드시 필요한 항목만 포함하도록 처리를 제한한다.
- 적용조건: 모든 개인정보처리자. 주로 관리자(개인정보취급자) 화면이 대상이며, 이용자 화면도 같은 원칙으로 점검한다.
- 점검유형: 관찰
- 점검위치: 관리자 회원 목록·상세, 주문·배송·상담 목록, 통계 화면. 이용자 마이페이지, 주문내역, 영수증·증명서 출력 화면.
- 점검방법:
  1. 화면별로 표시되는 개인정보 항목을 기록한다. 기록은 항목명만 하고 값은 남기지 않는다.
  2. 그 화면의 용도(예: 배송 처리, 상담 응대)에 비해 불필요한 항목이 있는지 표시한다. 예:
     - 목록 화면에 주민번호, 생년월일 전체, 상세 주소, 계좌번호가 노출된다.
     - 상담 화면에 결제 정보가 노출된다.
  3. 목록 화면과 상세 화면의 항목이 차등화되어 있는지 확인한다(목록은 최소, 상세는 필요 시).
  4. 권한별 계정이 있으면 사용자 승인 하에 권한별 화면 항목 차이를 비교한다.
- 양호기준: 화면마다 용도에 필요한 항목만 표시되고, 목록·상세·권한별로 차등화되어 있다.
- 취약기준: 다음 중 하나라도 해당하면 취약이다.
  - 용도와 무관한 개인정보 항목이 일괄 표시된다.
  - 목록 화면에 고유식별정보·카드·계좌번호 전체가 평문으로 나온다.
- 주의(추가 확인 필요): 용도 판단이 애매하면 "주의"로 기록하고 업무 담당자 확인을 요청한다.
- 조치방안:
  - 화면별 "용도-출력항목" 매핑표를 작성해 내부 관리계획이나 지침에 반영한다.
  - 목록에서 고유식별정보, 카드·계좌번호, 상세주소를 제거하거나 마스킹한다.
  - 상세 조회는 권한·사유 기반으로 "마스킹 해제" 기능을 둔다. 해제 행위는 접속기록에 남긴다.
  - 근거: 안내서 p.106(차등 표시·마스킹 예시)
- 증적: 화면 캡처(개인정보 값 전체 마스킹 필요), 화면별 항목 목록
- 비고: 법령 의무는 용도 특정과 최소화이고, 마스킹은 수단 중 하나다(FAQ 10-2, 의무 아님). "최소" 판단에는 업무 맥락이 필요하므로, 명백한 과다 노출만 취약으로 하고 나머지는 주의로 둔다.

### SAFE-12-01-02 마스킹 적용과 화면 간 일관성
- 근거: 고시 제12조제1항; 안내서 p.106(여러 시스템이 각기 다른 방식으로 마스킹하면 조합 위험이 있으므로 동일한 표시제한 필요); FAQ 10-2(p.152)
- 요구사항: 마스킹으로 출력항목을 최소화할 때는 화면이나 시스템마다 마스킹 위치가 달라 조합으로 원본이 복원되지 않도록 일관된 기준을 수립·적용하는 것이 바람직하다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 관찰
- 점검위치: 같은 정보주체가 표시되는 여러 화면(관리자 목록·상세·주문·상담·엑셀 미리보기). 이용자 화면(마이페이지, 주문내역, 배송지 관리, 알림 문구).
- 점검방법:
  1. 같은 항목(이름, 휴대전화, 이메일, 주소, 생년월일, 카드·계좌번호)의 마스킹 위치를 화면별로 비교한다.
  2. 예를 들어 A 화면 `010-****-1234`, B 화면 `010-1234-****`이면 조합으로 전체 번호가 나온다. 이런 사례를 기록한다.
  3. 화면에는 마스킹되어 있는데 DOM·응답에는 원본이 있는지는 SAFE-12-01-03에서 함께 본다.
  4. 증적에는 마스킹 패턴만 남긴다(예: `010-****-XXXX`).
- 양호기준: 항목별 마스킹 위치가 모든 화면에서 같다.
- 취약기준: 화면 간 마스킹 위치가 달라 두 화면을 조합하면 원본이 복원된다.
- 주의(추가 확인 필요): 일부 화면만 마스킹이 빠졌으면 "주의"로 기록한다.
- 조치방안: 전사 공통 마스킹 규칙을 수립하고 서버 공통 함수로 일괄 적용한다(안내서 p.106). 아래 위치 예시는 이 안내서 범위 밖의 업계 관행 예시이고, 확정은 사용자가 결정한다.
  - 이름: 두 번째 글자 마스킹
  - 휴대전화: 가운데 자리 마스킹
  - 이메일: 아이디 일부 마스킹
  - 주민번호: 뒤 6자리 마스킹
  - 카드번호: 7~12번째 자리 마스킹
  - 계좌번호: 일부 자리 마스킹
  - 주소: 상세주소 마스킹
- 증적: 화면별 마스킹 패턴 비교표, 캡처(원본 값 마스킹)
- 비고: 안내서 표현은 "바람직" 또는 "필요"이고 마스킹 자체는 의무가 아니다. 일관성 미흡은 조합 복원이 실제로 가능할 때만 취약으로 한다. 구체 마스킹 위치는 이 안내서에 없다(메모 참조).

### SAFE-12-01-03 웹페이지 소스·응답 본문·JS 변수·브라우저 저장소의 불필요한 개인정보 노출
- 근거: 고시 제12조제1항; 안내서 p.107("웹페이지 소스 보기 등을 통하여 불필요한 개인정보가 출력되지 않도록 조치"); 고시 제7조제2항(고유식별·카드·계좌, 참고); 법 제24조의2
- 요구사항: 화면에 보이지 않더라도 페이지 소스, 숨김 필드, API 응답, JS 변수로 불필요한 개인정보가 출력되면 안 된다. 특히 주민등록번호 등 고유식별정보, 카드번호, 계좌번호가 평문 전체로 내려오면 안 된다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 관찰
- 점검위치: 전 화면. 특히 마이페이지, 회원정보 수정, 주문·결제 내역, 환불계좌, 관리자 회원 목록·상세, 검색 결과, 자동완성 API.
- 점검방법:
  1. 페이지 소스와 DOM을 확인한다.
     - `document.querySelectorAll('input[type=hidden]')`의 name·value 패턴을 본다.
     - HTML 주석과 `data-*` 속성에 개인정보가 있는지 본다.
  2. 네트워크 응답(JSON)을 확인한다.
     - 화면 표시 항목보다 많은 필드가 내려오는지 본다(예: 목록 API에 주민번호, 생년월일, 전체 주소, 비밀번호 해시).
     - 화면은 마스킹인데 응답은 원본인지 본다.
  3. JS 전역 변수(`window.__INITIAL_STATE__`, `__NEXT_DATA__`, `__NUXT__` 등)를 확인한다.
  4. 브라우저 저장소(`localStorage`, `sessionStorage`)를 확인한다.
  5. 위 결과에 정규식을 적용한다.
     - 주민·외국인등록번호: `\b\d{6}-?[1-8]\d{6}\b`
     - 카드번호: `\b\d{4}[- ]?\d{4}[- ]?\d{4}[- ]?\d{3,4}\b`
     - 여권번호: `[A-Z]\d{8}` 또는 `[MSRODG]\d{3}[A-Z]\d{4}`
     - 운전면허번호: `\d{2}-?\d{2}-?\d{6}-?\d{2}`
     - 계좌번호: 숫자·하이픈 10~14자리, 필드명 `account`, `acctNo`, `bankAccount`
     - 결과는 건수와 필드명만 기록한다.
  6. 콘솔 로그(`console.log`)에 개인정보 객체가 출력되는지 확인한다.
- 양호기준: 응답·소스·저장소에 화면 용도에 필요한 항목만 있고, 마스킹 대상은 서버에서 마스킹된 값으로 내려온다. 고유식별정보, 카드·계좌번호 전체가 평문으로 나타나지 않는다.
- 취약기준: 다음 중 하나라도 해당하면 취약이다.
  - 화면에 표시하지 않는 고유식별정보, 카드·계좌번호, 비밀번호(해시 포함)가 응답·숨김필드·JS 변수·저장소·콘솔에 평문으로 존재한다.
  - 화면은 마스킹하지만 응답은 원본이다(클라이언트 측 마스킹).
- 주의(추가 확인 필요): 일반 개인정보(이름, 연락처 등)가 화면보다 과다하게 응답되면 "주의" 또는 "취약"으로 기록한다. 판단 기준은 메모를 참조한다.
- 조치방안:
  - 서버에서 화면용 DTO를 분리해 필요한 필드만 직렬화하고, 마스킹은 서버에서 한다.
  - 숨김필드에 개인정보를 두지 말고 식별 키만 둔다.
  - SSR 초기 상태에서 개인정보를 제거하고, 운영 빌드에서 `console.log`를 제거한다.
  - 고유식별정보와 카드·계좌번호는 표시가 필요할 때만 권한·사유 확인 후 별도 API로 제공한다.
  - 근거는 안내서 p.107(소스 보기 노출 금지)이고, 구현 방식은 점검자 권고다.
- 증적: 해당 요청 URL, 필드명 목록, 정규식 일치 건수. 값은 반드시 마스킹한다. 원본 응답 전문은 보고서에 첨부하지 않는다.
- 비고:
  - 법령 의무(제12조제1항)를 안내서 주의사항으로 구체화한 항목이다.
  - 이용자 본인의 정보를 본인 화면에 표시하는 것은 출력 용도에 맞으면 허용된다. 그래도 고유식별정보 전체 평문 응답은 취약으로 본다(주민번호 처리 제한 취지, 법 제24조의2). 이 판단은 사용자 확인이 필요하다(메모 참조).
  - 다른 정보주체의 데이터가 응답에 섞여 나오면 접근통제(제5·6조) 결함일 수 있으므로 해당 항목과 연결한다. 이 경우에도 파라미터를 변조해 재현하지 않는다.

### SAFE-12-01-04 개인정보 검색 조건 제한(like 검색 제한, 일치검색)
- 근거: 고시 제12조제1항; 안내서 p.107(업무상 필요하지 않으면 like 검색 금지, equal 검색 또는 2개 이상 조건 사용)
- 요구사항: 개인정보 검색 시 불필요하거나 과도한 정보가 조회되지 않도록, 업무상 반드시 필요한 경우가 아니면 부분일치(like) 검색을 막는다. 대신 일치검색(equal)이나 2개 이상 검색조건을 쓴다.
- 적용조건: 개인정보 검색 기능이 있는 개인정보처리시스템(주로 관리자 화면)
- 점검유형: 관찰. 실제 검색 실행은 능동(승인).
- 점검위치: 관리자 회원·고객 검색, 주문 검색, 상담 검색 화면
- 점검방법:
  1. 검색 화면의 UI를 확인한다(관찰).
     - 필수 검색조건 수
     - 조건 없이 "전체 조회"가 가능한지
     - 이름 한 글자 입력 허용 여부(`minlength`, `required` 속성, 안내 문구)
  2. 화면 진입 시 조건 없이 전체 목록이 자동 조회되는지 본다(첫 화면 자동 조회).
  3. 실제 부분검색 시험(예: 성씨 한 글자 검색)은 다른 정보주체의 개인정보를 대량 조회하게 되므로 기본적으로 하지 않는다. 필요하면 사용자 승인 후 사용자가 직접 실행하고, 결과는 건수만 기록한다.
- 양호기준: 검색 시 2개 이상 조건이나 정확 일치가 요구되고, 전체·부분 검색이 업무상 필요한 권한자로 제한된다. 첫 화면에서 개인정보 목록이 자동 표시되지 않는다(또는 마스킹되어 표시된다).
- 취약기준: 조건 없이 전체 회원 목록이 조회된다. 한 글자 부분검색으로 대량 개인정보가 평문으로 나온다.
- 주의(추가 확인 필요): 업무 필요성이 입증되지 않은 like 검색만 있으면 "주의"로 기록한다.
- 조치방안:
  - 검색조건을 2개 이상 필수로 한다(예: 이름+휴대전화 뒤 4자리). 기본은 일치검색으로 한다.
  - 부분검색은 권한자에게만 허용하고, 검색 결과 건수에 상한을 둔다.
  - 첫 화면 자동 조회를 제거한다(안내서 p.107 예시).
- 증적: 검색 화면 캡처(결과 값 마스킹), 폼 속성
- 비고: 안내서 주의사항(권고 성격)이다. 법령 위반 판정은 과다 조회가 명백할 때만 한다.

### SAFE-12-01-05 개인정보 다운로드(파일생성) 기능의 사유 입력·권한·항목 선택
- 근거: 고시 제12조제1항(파일생성 시 용도 특정·항목 최소화); 고시 제8조제2항(다운로드 상황 점검); 고시 제6조의2제1항제2호(다운로드 가능 취급자, 참고); 고시 제17조제1항(공공시스템 사전승인·사후소명); 안내서 p.94~95(다운로드 정의, 대량 다운로드 비정상 행위), p.106, p.130(사전승인 시 목적·필요성 기재); 안내서 p.107(엑셀 숨겨진 필드 금지)
- 요구사항: 다운로드(파일생성)도 출력에 해당하므로 다음을 지켜야 한다.
  - 용도를 특정하고 항목을 최소화한다.
  - 다운로드 상황은 점검할 수 있어야 한다.
  - 엑셀 등에 개인정보가 숨겨진 필드로 저장되지 않아야 한다.
  - 공공시스템은 이상행위 기준에 해당하는 다운로드에 사전승인이나 사후소명 절차가 있어야 한다.
- 적용조건: 개인정보 다운로드 기능이 있는 모든 개인정보처리자. 사전승인·소명 의무는 공공시스템운영기관에 해당한다.
- 점검유형: 능동(승인). UI 관찰은 관찰.
- 점검위치: 관리자 화면의 엑셀·CSV·PDF 내보내기, 대량 출력, 인쇄 기능
- 점검방법:
  1. 관찰:
     - 다운로드 버튼의 노출 범위(어느 권한 계정에 보이는지)를 확인한다.
     - 버튼 주변 옵션을 확인한다: 항목 선택 체크박스, 마스킹 포함·해제 옵션, 건수 제한 안내.
  2. 능동(승인):
     - 사용자 승인 후 테스트 범위로 다운로드 버튼을 누르고 다음을 확인한다.
       - 사유 입력창이 뜨는지
       - 사유가 필수인지(빈 값 제출 시 차단되는지)
       - 사유가 미리 정한 선택지인지 자유입력인지
       - 승인 요청 절차가 있는지
     - 사유 입력 단계에서 취소할 수 있으면 실제 파일을 생성하지 않고 확인을 끝낸다.
  3. 파일을 생성한다면 사용자가 열어 숨김 시트·숨김 열·불필요 항목 포함 여부와 마스킹 여부를 확인해 알려준다. Claude는 파일 내용을 보지 않는다.
  4. 권한별 계정이 있으면 하위 권한 계정에서 다운로드 버튼이 숨겨지거나 비활성화되는지 비교한다.
- 양호기준:
  - 다운로드가 필요한 권한자에게만 제공된다.
  - 용도(사유) 입력이나 선택이 필수다.
  - 필요한 항목만 선택하거나 마스킹해 내려받을 수 있다.
  - 숨김 필드가 없다.
  - 다운로드 이력이 접속기록에 남는다(서면 확인).
- 취약기준: 모든 관리자 계정이 사유나 항목 선택 없이 전체 항목을 평문으로 내려받을 수 있다. 내려받은 파일에 화면보다 많은 항목이나 숨김 필드가 있다.
- 주의(추가 확인 필요):
  - 사유 입력이 없더라도 항목 최소화와 다운로드 점검이 서면으로 확인되면 "주의"로 기록한다(일반 개인정보처리자).
  - 공공시스템에서 사전승인·사후소명이 모두 없으면 취약이다.
- 조치방안:
  - 다운로드 클릭 시 사유 입력 모달을 띄운다. 예: 사유 선택(배송, 정산, 민원 등)과 상세사유 입력, 빈 값 제출 차단.
  - 다운로드 항목을 선택하게 하고 기본은 마스킹으로 한다.
  - 건수 상한과 대량 다운로드 시 상급자 승인을 둔다.
  - 파일 암호를 설정한다(SAFE-07-05-03).
  - 다운로드 이력을 별도로 기록해 정기 점검한다(제8조제2항).
  - 공공시스템은 사전승인 또는 사후소명 워크플로를 둔다(안내서 p.130, FAQ 14-3).
  - 사유 입력 화면은 안내서에 명시된 형태가 아니라 점검자 권고 구현 예시다.
- 증적: 다운로드 버튼·옵션·사유 입력 화면 캡처, 권한별 비교 결과. 파일 내용은 캡처하지 않는다.
- 비고:
  - 일반 개인정보처리자에게 "다운로드 사유 입력"을 명시한 조문은 없다. 제12조제1항의 용도 특정을 구현하는 대표 수단이다.
  - 공공시스템은 제17조제1항과 안내서 p.130에 따라 사전승인(목적·필요성 기재) 또는 사후소명이 요구된다.
  - 다운로드를 실행하면 운영 접속기록에 남으므로 반드시 사전 승인을 받는다.

### SAFE-12-02-01 출력·복사물 안전관리
- 근거: 고시 제12조제2항; 안내서 p.107(출력·복사물 안전조치 예시, DRM·보안 USB·DLP)
- 요구사항: 개인정보가 포함된 종이 인쇄물과 외부 저장매체 복사물을 안전하게 관리하기 위해 출력·복사 기록 등 필요한 안전조치를 해야 한다. 안내서 예시는 다음과 같다.
  - 정책, 대장, 관리부서
  - 외부반출 통제
  - 인쇄자·인쇄일시 기록
  - 파기계획
  - 복합기 보안
  - 워터마크
  - DRM, DLP
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면. 인쇄 화면은 관찰 보조.
- 점검위치: (관찰 보조) 관리자·이용자 인쇄 기능, 출력용 화면
- 점검방법:
  - 서면 확인: 출력·복사물 관리 지침, 출력 기록(인쇄자·일시), DRM·DLP·보안 USB 적용 현황, 종이 파기 기록을 요청한다.
  - 관찰 보조: 인쇄용 화면이나 출력 미리보기 페이지에 워터마크와 출력자·일시 표시가 있는지 본다. 인쇄 버튼은 브라우저 인쇄 대화상자만 열고 실제 인쇄는 하지 않는다. 또는 `@media print` CSS를 조회한다.
- 양호기준: 지침과 기록이 있고 기술적 통제(DRM, 워터마크 등)를 적용한다.
- 취약기준: 출력·복사물 관리 조치가 없다.
- 조치방안: 안내서 p.107 예시를 참고해 다음을 갖춘다.
  - 출력·복사물 관리 지침
  - 생산·관리 대장
  - 출력물 워터마크(출력자 ID, 일시)
  - DRM 또는 DLP
- 증적: 서면 자료, 인쇄 화면 캡처(마스킹)
- 비고: 법령 의무다. 구체 수단은 안내서 예시다.

## 제13조 개인정보의 파기

### SAFE-13-01-01 파기 방법(완전파괴·소자·초기화·덮어쓰기)
- 근거: 고시 제13조제1항; 안내서 p.108~109(복원 불가능한 방법, 매체별 방법, 완전포맷·덮어쓰기 3회 이상 권고, 파기 기록 관리)
- 요구사항: 개인정보를 파기할 때는 다음 가운데 하나를 해야 한다.
  - 완전파괴(소각, 파쇄)
  - 전용 소자장비(디가우저)로 삭제
  - 복원되지 않도록 초기화나 덮어쓰기
  - 메모리 저장장치(SSD 등)는 완전파괴나 초기화·덮어쓰기를 적용한다.
  - 파기 시행과 결과 확인은 개인정보 보호책임자 책임하에 하고 기록·관리한다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 파기 절차서, 파기 관리대장, 매체 폐기 증명서(위탁 시), 파기 결과 확인 기록을 요청한다.
- 양호기준: 매체별로 고시 방법으로 파기하고 기록을 관리한다.
- 취약기준: 단순 삭제나 포맷 후 매체를 재사용·폐기하고 기록이 없다.
- 조치방안: 매체별 파기 방법을 규정하고 파기대장을 운영한다.
  - HDD: 디가우저 또는 파쇄
  - SSD: 파쇄 또는 암호화 후 키 폐기
  - 종이: 세절 또는 소각
  - 덮어쓰기 3회 이상은 안내서 권고다.
- 증적: 서면 자료
- 비고: 법령 의무다. "3회 이상"은 안내서 권고 수치다. 탈퇴 회원의 즉시 파기 여부 같은 파기 시점은 「개인정보 보호법」 제21조 담당 범위다.

### SAFE-13-02-01 일부 파기 시 조치
- 근거: 고시 제13조제2항제1·2호; 안내서 p.110(일부 파기 사례, 삭제 방법 예시, 복구 관련 모니터링, 서면 마스킹·절삭)
- 요구사항: 개인정보 일부만 파기할 때 제1항 방법이 어려우면 다음 조치를 한다.
  - 전자적 파일: 삭제 후 복구·재생되지 않도록 관리·감독한다.
  - 기록물, 인쇄물, 서면: 해당 부분을 마스킹하거나 구멍 뚫기 등으로 삭제한다.
  - 운영 DB에서 탈퇴 회원 삭제, 백업 매체의 특정 정보주체 삭제 등이 포함된다.
- 적용조건: 모든 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 DB 일부 파기 절차(삭제 쿼리·배치), 백업본 처리 방법, 복구 활동 모니터링 기록을 요청한다.
- 양호기준: 절차가 있고 백업까지 포함해 관리한다.
- 취약기준: 운영 DB에서만 삭제하고 백업에는 그대로 남아 있는데 관리 방안이 없다.
- 조치방안:
  - 파기 배치에 백업 처리 방안을 포함한다(파기 대상 제외 백업 등).
  - 복구 작업 승인과 모니터링 절차를 둔다(안내서 예시).
- 증적: 서면 자료
- 비고: 법령 의무다.

### SAFE-13-03-01 기술적 특성으로 파기가 곤란한 경우 익명처리
- 근거: 고시 제13조제3항; 법 제58조의2; 안내서 p.111(블록체인 오프체인 저장, 해시 등 익명정보만 온체인, 파기 시 솔트·키 삭제)
- 요구사항: 블록체인처럼 제1·2항 방법으로 파기하기 현저히 곤란하면 익명정보로 처리해 복원이 불가능하도록 해야 한다.
- 적용조건: 블록체인 등 수정 불가 기술을 쓰는 개인정보처리자
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 온체인·오프체인 데이터 설계서와 파기 시 솔트·키 삭제 절차를 요청한다.
- 양호기준: 온체인에는 익명정보만 있고 오프체인은 파기할 수 있다.
- 취약기준: 개인정보가 온체인에 평문이나 복원 가능한 형태로 기록된다.
- 조치방안: 개인정보를 오프체인으로 분리하고, 온체인에는 솔트를 적용한 해시만 기록하며, 파기 시 솔트·키를 삭제한다(안내서 예시).
- 증적: 서면 자료
- 비고: 법령 의무다. 해당 기술을 쓰지 않으면 "해당없음"이다.

## 제3장 공공시스템운영기관 등 (제14조~제18조)

### SAFE-14-01-01 공공시스템 지정 여부 확인(제3장 적용 판단)
- 근거: 고시 제14조제1항제1~3호, 제2항; 영 제30조의2제1항; 안내서 p.112~115(유형 정의, 지정 제외 예시); FAQ 11-1·11-2·11-3(p.153)
- 요구사항: 다음 시스템 가운데 보호위원회가 지정한 공공시스템을 운영하는 공공기관은 제2장 외에 제3장 조치를 해야 한다.
  - 단일접속 시스템: 100만명 이상, 취급자 200명 이상, 민감정보 중 하나
  - 표준배포 시스템: 대국민 행정·민원용
  - 개별 시스템: 100만명 이상, 취급자 200명 이상, 주민등록정보시스템 연계, 총사업비 100억원 이상 중 하나

  지정은 보호위원회가 하고 홈페이지(pipc.go.kr)에 공지한다. 지정 제외 사유는 다음과 같다.
  - 체계적 검색 곤란(PDF·이미지 내 텍스트)
  - 내부 업무용(ERP 등)
  - 유출 가능성 낮음

  위반하면 3,000만원 이하 과태료(법 제75조제2항제5호)이고, 유출 시 과징금 대상이 될 수 있다.
- 적용조건: 공공기관
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 보호위원회 지정 공문이나 공지 목록에 해당 시스템이 있는지 사용자(기관)에게 확인한다.
- 양호기준: (판정용) 지정 여부가 명확하다.
- 취약기준: (판정용) 지정 여부가 명확하지 않다.
- 조치방안: 해당하면 SAFE-15~18 항목을 적용하고, 지정 여부를 기관 내부 관리계획에 명시한다.
- 증적: 지정 공문·공지 사본
- 비고:
  - 판정 항목이 아니라 적용범위 결정 항목이다. 지정되지 않았으면 SAFE-15~18은 "해당없음"이다.
  - 제외 시스템도 추가 조치는 권장 사항이다(안내서 p.115).
  - 이용기관(공공시스템에 접속하는 기관)은 SAFE-16-05-01과 SAFE-17-02-01의 이용기관 측 이행이 해당한다.

### SAFE-15-00-01 공공시스템별 내부 관리계획 수립·시행
- 근거: 고시 제15조제1~5호; 영 제30조의2제1항제1호, 제3~5항; 안내서 p.116~121(별지·유형별 수립 가능, 관리책임자 연 1회 이행실태 점검, 협의회 연 1회 이상 개최, 취급자 역할 예시); FAQ 12-1~12-4(p.156)
- 요구사항: 공공시스템별로 다음 사항을 포함한 내부 관리계획을 수립·시행해야 한다.
  1. 관리책임자(시스템 총괄부서의 장) 지정
  2. 관리책임자의 역할과 책임
  3. 개인정보취급자의 역할과 책임
  4. 제4조제1항제4~6호, 제8호(취급자 관리·교육, 접근권한, 접근통제, 접속기록)
  5. 제16조~제18조 사항

  기관 내부 관리계획의 별지나 유형별 묶음으로 수립할 수 있다. 관리책임자는 연 1회 이상 이행실태를 점검한다. 공공시스템운영협의회는 연 1회 이상 개최한다(안내서). 전담부서나 인력을 둔다(영).
- 적용조건: 공공시스템운영기관
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 공공시스템별 내부 관리계획(또는 별지), 관리책임자 지정 문서, 협의회 구성·회의록, 이행실태 점검 결과를 요청한다.
- 양호기준: 1~5호가 모두 포함되고, 지정·점검·협의회가 이행된다.
- 취약기준: 시스템별 계획이 없거나 항목이 누락되었다. 관리책임자가 지정되지 않았다.
- 조치방안:
  - 기관 내부 관리계획에 공공시스템별 별지를 추가한다(FAQ 12-2).
  - 관리책임자 지정 공문을 내고 역할을 규정한다. 안내서 p.118 예시는 다음과 같다.
    - 협의회 참석
    - 사후통지
    - 연 1회 점검
    - 반기 권한 점검
    - 이용기관 교육
    - 이용기관 월 1회 접속기록 점검 관리
  - 협의회를 설치하고 연 1회 이상 개최한다.
- 증적: 서면 자료
- 비고:
  - 법령 의무다. 현행 고시 제15조제5호는 "제16조부터 제18조까지"이고, 그 가운데 제18조 부분은 2027.1.1. 시행이다(고시 부칙).
  - 안내서(p.116)는 "제16조 및 제17조"로 적혀 있어 구 고시 기준이다.
  - 협의회 연 1회와 이용기관 월 1회 점검은 안내서(강화계획) 기준이다.

### SAFE-16-01-01 공공시스템 접근 권한과 인사정보 연계
- 근거: 고시 제16조제1항; 영 제30조의2제1항제2호; 안내서 p.122~124(e인사·표준지방인사·정부디렉토리 연계, 퇴직·휴직·징계·부서이동 시 자동 말소, 팀 내 업무 변경은 관리책임자가 현행화); FAQ 13-1·13-2·13-4·13-5·13-7·13-11·13-12(p.157~160)
- 요구사항: 공공시스템 접근 권한을 부여·변경·말소할 때는 인사정보와 연계해야 한다. 원칙은 자동 연계이고, 소속부서까지 연계하면 된다. 자동 연계가 곤란하면 인사 변동 시 지체 없이 변경하는 절차를 둔다. DB 접근통제 솔루션의 권한도 연계 대상이다.
- 적용조건: 공공시스템운영기관
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 인사정보 연계 구성도, 연계 대상 인사시스템, 자동 말소 처리 로그, 최근 인사이동자의 권한 변경 내역을 요청한다.
- 양호기준: 인사 변동이 지체 없이 자동으로 반영되고 말소된다.
- 취약기준: 연계가 없고 수동 절차도 없다. 퇴직자나 전보자 계정이 남아 있다.
- 조치방안:
  - e인사, 표준지방인사, 정부디렉토리와 연계한다.
  - 연계가 곤란하면 인사발령 시 권한 변경 매뉴얼을 운영한다(안내서 p.124 예시).
  - DB 접근통제 솔루션도 연계한다(FAQ 13-11).
- 증적: 서면 자료
- 비고: 법령 의무다.

### SAFE-16-02-01 인사정보 미등록자 계정 발급 제한
- 근거: 고시 제16조제2항; 고시 제5조제3항·제4항; 안내서 p.124~125(불가피한 사유 예시: 위탁 공공기관, 유지보수 업체, 수탁 단체 직원; 최소 범위, 3년 보관, 목적 달성 시 지체 없이 말소); FAQ 13-8(p.158)
- 요구사항: 인사정보에 등록되지 않은 자에게는 계정을 발급하면 안 된다. 긴급상황 등 불가피한 사유가 있으면 예외로 하되, 다음을 지킨다.
  - 사유를 권한 부여 내역에 포함한다.
  - 내역을 3년 보관한다.
  - 권한은 최소 범위로 부여한다.
  - 목적을 달성하면 즉시 말소한다.
- 적용조건: 공공시스템운영기관. 직접 발급하는 이용기관도 포함한다(제16조제5항).
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 미등록자 계정 목록, 발급 사유 기록, 말소 내역을 요청한다.
- 양호기준: 모든 미등록자 계정에 사유 기록이 있고 기한 관리가 된다.
- 취약기준: 사유 기록이 없거나 목적 달성 후에도 계정이 유지된다.
- 조치방안: 미등록자 계정 발급 신청서에 사유와 기간을 필수로 넣고, 만료일 자동 잠금을 적용하고, 권한 내역을 3년 보관한다.
- 증적: 서면 자료
- 비고: 법령 의무다.

### SAFE-16-03-01 계정 발급 시 개인정보 보호 교육·보안서약
- 근거: 고시 제16조제3항; 안내서 p.125~126(행동수칙 고지로 교육 대체 가능, 표준행동수칙 10개 항목, 비공무원 부서장의 신청서·서약서·교육실적 보관, 회원가입·가입승인 과정에서 팝업으로 확인·동의하는 온라인 방식 권장); FAQ 13-6·13-9·13-10(p.158~159)
- 요구사항: 계정을 발급할 때 개인정보 보호 교육을 실시하고 보안서약을 받아야 한다. 행동수칙 고지로 교육을 대체할 수 있다. 민간인 사용자도 대상이다. 온라인(시스템 내 팝업 동의)이나 공문 방식 모두 가능하며, 공문 방식이면 증빙을 보관한다.
- 적용조건: 공공시스템운영기관. 직접 발급하는 이용기관도 포함한다.
- 점검유형: 관찰. 발급 이력은 서면.
- 점검위치: 공공시스템의 사용자 계정 신청(회원가입) 화면, 가입승인 화면
- 점검방법:
  - 관찰: 계정 신청 화면에 개인정보 보호 행동수칙이나 교육 내용 고지와 보안서약 동의 체크가 있는지 화면만 확인한다. 신청서는 제출하지 않는다.
  - 서면: 계정 발급 대장과 보안서약서 및 교육 이수 증빙을 대조한다.
- 양호기준: 모든 발급 계정에 교육(또는 행동수칙 고지)과 보안서약 증빙이 있다.
- 취약기준: 서약이나 교육 없이 계정이 발급된다.
- 조치방안:
  - 계정 신청 화면에 표준행동수칙 고지와 보안서약 동의 단계를 넣는다(안내서 권장 온라인 방식).
  - 서약 이력을 계정과 연결해 보관한다.
- 증적: 신청 화면 캡처, 서면 자료
- 비고: 법령 의무다. 행동수칙 대체와 온라인 방식은 안내서 해석·권장이다.

### SAFE-17-01-01 접속기록 자동화 분석·이상행위 탐지·소명
- 근거: 고시 제17조제1항; 영 제30조의2제1항제3호, 제2항(권한 없는 접근 확인 시 정보주체 통지); 안내서 p.128~131(접속기록 검색 메뉴, 5개 항목 누락 사례, 이상행위 기준 예시, 사전승인·사후소명, 오남용 시 고발·징계); FAQ 13-3(p.157), 14-1~14-3(p.161)
- 요구사항: 공공시스템 접속기록을 자동화된 방식으로 분석해 불법 유출과 오·남용 시도를 탐지하고 사유를 소명하게 해야 한다. 이상행위 기준 예시는 다음과 같다.
  - 공휴일·업무시간 외 열람·다운로드
  - 직전 3개월 평균을 초과하는 열람·다운로드
  - 월별 다운로드 상위자
  - 월별 다수 IP 사용자

  사후소명 대신 사전승인도 가능하다. 자동점검이 구현되기 전에는 수시로 점검한다. 공무원과 비공무원 모두 대상이다. 권한 없는 접근이 확인되면 정보주체에게 통지한다(영).
- 적용조건: 공공시스템운영기관
- 점검유형: 서면. 기능 존재는 관찰 보조.
- 점검위치: (관찰 보조) 공공시스템 관리자 화면의 접속기록·이상행위·소명 메뉴
- 점검방법:
  - 서면 확인: 이상행위 탐지 기준서, 탐지·알림 내역, 소명·승인 처리 기록, 통지 사례를 요청한다.
  - 관찰 보조: 관리자 메뉴에 이상행위 탐지 결과, 소명 요청·처리, 사전승인 신청 메뉴가 있는지와 검색 조건을 화면으로 확인한다. 개인정보 값은 마스킹하고 처리 버튼은 누르지 않는다.
- 양호기준: 자동 탐지 기준이 설정·운영되고 소명이나 승인 절차가 이행된다.
- 취약기준: 자동 분석이 없고 수시 점검 기록도 없다. 탐지 후 소명 절차가 없다.
- 조치방안:
  - 안내서 p.130 예시 기준으로 이상행위 룰을 설정하고 알림 기능을 구현한다(직접 개발 또는 솔루션, FAQ 14-2).
  - 사전승인 또는 사후소명 워크플로를 둔다. 사후소명은 기준 해당 건을 모아 부서장이 정기 검토한다(FAQ 14-3).
  - 오·남용 확인 시 징계·고발 절차를 둔다.
- 증적: 메뉴 캡처(마스킹), 서면 자료
- 비고: 법령 의무다. 이상행위 기준 수치는 안내서 예시다.

### SAFE-17-02-01 이용기관용 접속기록 점검 기능 제공
- 근거: 고시 제17조제2항; 안내서 p.131(이용기관이 접속기록을 확인·분석할 수 있는 기능); 안내서 p.118(이용기관 월 1회 이상 점검 관리); FAQ 11-4 표(p.153~154)
- 요구사항: 공공시스템운영기관은 이용기관이 소관 취급자의 접속기록을 직접 점검할 수 있는 기능을 제공해야 한다.
- 적용조건: 공공시스템운영기관. 이용기관은 그 기능으로 점검을 이행한다.
- 점검유형: 관찰. 운영 실적은 서면.
- 점검위치: 공공시스템 관리자(이용기관 관리자 권한) 화면의 접속기록 조회 메뉴
- 점검방법:
  - 관찰: 사용자 승인 하에 이용기관 관리자 계정으로 로그인한다(입력은 사용자). 접속기록 조회 메뉴에서 다음을 화면으로 확인한다.
    - 소관 취급자 범위로 조회되는지
    - 검색 조건(기간, 사용자, 수행업무)이 있는지
    - 5개 항목 컬럼이 표시되는지
    - 다른 기관 기록이 섞여 보이지 않는지(보이는 것만 기록하고 파라미터는 변조하지 않는다)
  - 서면: 이용기관의 월 점검 기록을 요청한다.
- 양호기준: 이용기관이 소관 기록만 검색·분석할 수 있는 메뉴가 제공되고 실제로 활용된다.
- 취약기준: 기능이 없거나 운영기관에 요청해야만 기록을 받을 수 있다.
- 조치방안: 이용기관별로 범위가 제한된 접속기록 조회·통계·이상행위 화면을 구현하고, 월 1회 점검 결과 등록 기능을 둔다. 월 1회는 안내서 기준이다.
- 증적: 메뉴 화면 캡처(개인정보·식별자 마스킹)
- 비고: 법령 의무다.

### SAFE-18-01-01 공공시스템 취약점 점검 연 1회 이상
- 근거: 고시 제18조제1항; 고시 제4조제1항제10호(내부 관리계획의 취약점 점검 사항); 고시 부칙(2027.1.1. 시행); 참고: 안내서 부록 위험도 분석 25번(p.184, 웹 취약점 연 1회 이상 진단, 긴급 취약점 추가 점검)

- 증적: 서면 자료
- 비고:
  - 법령 의무지만 시행 전(점검일 2026-10-27 기준)이다. 시행 전에는 "참고(시행 예정)"로 보고한다.
  - 안내서(2025.11)에는 이 조의 해설이 없다.
  - 이 점검 도구의 웹 관찰 결과는 취약점 점검을 대신하지 않는다.

### SAFE-18-03-01 점검 결과 보완조치
- 근거: 고시 제18조제3항; 고시 부칙(2027.1.1. 시행)
- 요구사항: 취약점 점검과 침투테스트 결과에 따라 필요한 보완조치를 지체 없이 시행해야 한다.
- 적용조건: 공공시스템운영기관. 2027.1.1.부터 시행한다.
- 점검유형: 서면
- 점검위치: -
- 점검방법: 서면 확인으로 발견 취약점별 조치 계획과 조치 완료 증적, 이행 점검 결과를 요청한다.
- 양호기준: 모든 발견 사항에 조치 또는 위험수용 결재가 있고 지체되지 않았다.
- 취약기준: 미조치 취약점이 방치되어 있다.
- 조치방안: 취약점별 조치 기한(위험도별)과 이행 점검 절차를 두고, 결과를 관리책임자에게 보고한다.
- 증적: 서면 자료
- 비고: 법령 의무이며 시행 예정이다.

### 원문 간 불일치(현행 고시 기준으로 작성)
1. 제18조 신설:
   - 현행 고시 제18조(공공시스템 취약점 점검·침투테스트)와 제15조제5호의 "제18조" 부분은 2027.1.1. 시행이다.
   - 안내서는 제18조를 "재검토 기한"으로, 제15조제5호를 "제16조 및 제17조"로 적는다(구 고시 기준).
   - 안내서 제15조 조문은 "수립하여야 한다"이고, 현행 고시는 "수립·시행하여야 한다"다.
2. 제8조 시행시기:
   - 안내서는 제8조제1항 2년 보관과 제2항 다운로드 점검을 "'26.11.1 부 시행"으로 표시한다(고시 제2025-9호 부칙, 발령 1년 후).
   - 현행 고시 제2026-9호 부칙에는 이 유예가 다시 적혀 있지 않다. 다만 종전 부칙의 경과규정은 유지되는 것으로 보았다.
   - 점검일(2026-10-27)은 시행 직전이다. 2026.11.1. 이후 점검분부터 적용할지, 지금부터 "시행 예정"으로 표기할지 사용자 결정이 필요하다.
3. 제14~17조 시행일: 안내서는 2024.9.15. 시행으로 적는다. 현행 고시에서도 계속 유효하다.
4. 제7조 본문은 안내서와 현행 고시가 같다.

### 판정 기준 중 사용자 결정이 필요한 점
1. TLS 버전 기준:
   - 고시와 안내서에 TLS 버전 수치가 없다. 안내서 p.83은 알고리즘 표와 TDEA·MD5·SHA-1 금지만 있고, 부록 제3장은 웹사이트 목록뿐이다.
   - "TLS 1.2 이상"을 점검자 기준으로 취약 판정할지, 주의로 둘지 정해야 한다.
   - TLS 버전과 암호군은 브라우저 JS로 확인할 수 없다. openssl 같은 별도 도구를 쓸지(사용자 실행), 외부 진단 서비스를 쓸지(도메인 제3자 전달) 정해야 한다.
2. 마스킹 위치:
   - 이 안내서에는 항목별 마스킹 위치 기준이 없다(FAQ 10-2: 마스킹은 의무 아님, 일관성 권고).
   - 이름, 전화, 이메일, 카드번호 등의 위치 기준을 다른 출처(예: 표준 개인정보 보호지침, 업계 관행)에서 가져올지 결정이 필요하다.
3. 본인 화면의 고유식별정보 전체 표시:
   - 이용자 본인 화면·응답에 주민번호, 카드·계좌번호 전체가 평문으로 내려오는 경우의 판정이 필요하다.
   - 제12조 문언상 용도에 맞으면 허용될 수 있으나, 이 문서는 "취약"(불필요 출력)으로 제안했다.
4. 일반 개인정보의 과다 응답: 이름, 연락처 등이 화면 표시보다 API 응답에 많이 내려오는 경우를 취약으로 할지 주의로 할지 기준이 필요하다.
5. 다운로드 사유 입력:
   - 일반 개인정보처리자에게는 명문 의무가 아니다(제12조제1항 용도 특정의 구현 수단).
   - 미구현 시 "주의"로 제안했다. 공공시스템은 제17조에 따라 사전승인 또는 사후소명이 없으면 취약이다.
6. 능동(승인) 항목: 다운로드 실행, 비밀번호 찾기 실행, 검색 실행은 운영 접속기록에 남고 메일 발송이 생길 수 있다. 실행 여부와 범위를 항목마다 승인받는 절차를 스킬에 반영해야 한다.
7. 브라우저 저장소의 개인정보:
   - 관리자 PC의 localStorage 개인정보를 제7조제5항(취급자 컴퓨터 저장 암호화) 위반으로 보는 것은 해석이다.
   - 이용자 측 저장소의 개인정보는 제12조 노출로만 다루었다.
8. 법령 해석 기반 판정 항목: URL에 비밀번호가 실리는 경우, 혼합 콘텐츠, 토큰 저장 위치는 고시에 명문이 없고 제7조제1·4항의 해석으로 판정한다. 보고서에 "해석에 따른 판정"으로 표기할지 정해야 한다.
9. 제11조 ID: 제11조는 항 없이 호만 있어 `SAFE-11-00-0N`으로 했다. 제15조도 같은 이유로 `SAFE-15-00-01`이다. ID 규칙 확인이 필요하다.
10. 제18조 외부 전문기관 자격: "외부 전문기관·전문가"의 자격 요건이 고시에 없다. 판정 시 계약 주체가 외부인지만 볼지 결정이 필요하다.
