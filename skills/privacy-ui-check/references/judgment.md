# 판정과 위험도 기준

설계서 6장(docs/specs/2026-10-27-privacy-ui-check.md)을 점검 중에 바로 쓰도록 옮긴 것이다.

## 판정 5종

| 판정 | 뜻 | findings.json 위치 | 상세 페이지 |
|---|---|---|---|
| 취약 | 법령·고시 의무 위반이 화면·수집물에서 확인됨 | `findings` | 만든다 |
| 권고 | 의무 위반은 아니지만 안내서 예시·외부 기준에 못 미침, 또는 해석에 따른 판정 | `findings` | 만든다 |
| 양호 | 기준 충족 | `others` | 개요 집계만 |
| 점검불가 | 서면 항목, 승인하지 않은 능동 시험, 접근할 수 없는 화면 | `others` (+`request`) | 개요 목록 |
| 해당없음 | 적용조건 밖(intake.conditions 로 판단) | `others` (+`reason`) | 개요 목록 |

판정 순서:
1. 기준 항목의 `applies_when` 을 intake.conditions 와 대조한다. 해당하지 않으면 **해당없음**.
2. `type: 서면` 이면 **점검불가**(요청 자료 = 그 항목 `method` 의 "서면 확인:" 뒤 문서).
3. `type: 능동` 이면 승인·시험한 경우만 판정하고, 아니면 **점검불가**(사유: 미승인).
4. 수집물을 `pass`·`fail` 문구와 대조한다. `strength` 가 `의무` 이고 `fail` 에 해당하면 **취약**.
5. `strength` 가 `권고`·`외부참고` 이거나, 고시에 명문이 없어 해석으로 판정하면 **권고**. 근거 끝에 "(해석에 따른 판정)" 또는 "(외부 참고)" 를 적는다.

## 위험도(취약·권고에만)

| 위험도 | 기준 | 예 |
|---|---|---|
| 상 | 개인정보·인증정보가 권한 없는 자에게 바로 노출·탈취될 수 있음 | 평문 HTTP 로그인, 응답 속 주민번호 전체, 관리자 페이지 외부 노출, 인증 실패 제한 없음 |
| 중 | 다른 조건이 겹쳐야 노출되거나 정보주체 권리를 침해 | 세션 차단 없음, 마스킹 불일치, 동의 필수·선택 미구분, 처리방침 기재 누락 |
| 하 | 노출 가능성이 낮거나 형식 요건 미흡 | 처리방침 명칭·강조 표시, 권고 수준 항목 |

- 기준 항목의 `default_risk` 에서 시작해 실제 노출 범위(누가, 로그인 없이, 몇 명의 정보가)를 보고 올리거나 내린다. 바꿨으면 문제점 문구에 이유를 적는다.
- 같은 위험도 안에서는 취약이 권고보다 앞에 온다(리포트가 자동 정렬).

## 권고 기준값(법정 수치가 없는 항목)

고시·안내서가 수치를 정하지 않은 항목은 아래 값에 못 미치면 **권고**로 판정하고 근거에 "외부 참고"라고 적는다.
처리자가 자체 기준을 서면으로 제시하면, 그 기준과 실제 동작이 일치하는지를 본다.

| 항목 | 외부 참고값 |
|---|---|
| 비밀번호 작성 규칙 | 2종 조합 10자 이상 또는 3종 조합 8자 이상(구 해설서 관행), 추측 쉬운·유출 비밀번호 거부(NIST SP 800-63B) |
| 인증 실패 제한 | 5회 이내 잠금 또는 지연 |
| 세션 자동 차단 | 30분 이내 |
| TLS | TLS 1.2 이상(브라우저로 볼 수 없음 — 사용자가 실행한 openssl 결과가 없으면 점검불가) |
| 마스킹 | 같은 항목은 화면 간 같은 규칙(안내서 FAQ) |

## 문구 쓰는 법

- **취약점명**: 무엇이 어디서 어떻게 — "회원정보 수정 화면에 주민등록번호 전체가 표시됨".
- **문제점**: 번호 박스마다 한 줄. 화면에서 본 사실만 적고 개인정보 값은 쓰지 않는다(“주민등록번호 13자리 전체”처럼 형태로 적는다).
- **조치방안**: 기준 항목의 `remediation` 을 이 사이트 상황에 맞게 구체화한다(어느 화면·파라미터·헤더를 어떻게). 의무 조치와 권고 조치를 구분한다.
- **근거**: 조문(고시·법 제N조제N항), 근거 강도(의무·권고·외부참고), 안내서 쪽수. 기준 ID 는 `item_ids` 에 넣으면 리포트가 함께 보여 준다.
